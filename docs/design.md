# Design

This document is the source of truth for how taste-library behaves. Behavior is defined here before it is built, and a change that alters behavior updates this document in the same pull request. The on-disk data format is specified separately in [format-spec.md](format-spec.md), the public contract that the tool, agents and integrations follow.

Sections marked **(to specify in Mx)** are placeholders that the named milestone fills in.

## 1. Purpose and audience

taste-library helps people inject their own design taste into AI-assisted design and avoid generic, regressed-to-the-mean interfaces. It serves a method in three steps: build a taste library of high-quality references grouped into aesthetic families; use a few focused tools; and build in sequence, never in one shot, with prompts made of four elements (**Aesthetic, Reference, Intent, Guardrails**), several directions side by side, then refinement.

Audience: people who already use AI coding agents (Claude Code, Cursor, Codex and similar). No design or development background is assumed for using the app itself.

## 2. Principles

1. **Local-first and private.** Runs on the user's machine, works offline, needs no account, sends no telemetry.
2. **Plain files are the truth.** The library is a folder of small, readable files. Any index is disposable and rebuilt from the files.
3. **The user's words are sacred.** Notes are stored verbatim. Interpretation is a separate layer, marked `to-review` until accepted or corrected.
4. **Intent only from briefings.** A project takes from a briefing only what it is, for whom, what users must do and why. Visual decisions are filtered out and listed as discarded.
5. **Agents work on the same files**, but write only through `tastelib` (CLI or MCP), which validates every write.
6. **The tool produces inputs and takes outputs back.** It does not integrate specific design or image services; it exports what they consume and imports what they produce.

## 3. Architecture

A TypeScript monorepo (pnpm workspaces):

```
packages/
  core/     data format: schemas, validated read/write, index, migrations
  server/   local server: API, URL capture, compression, video
  web/      user interface (React), translations en / pt-BR
  cli/      the `tastelib` command (init, open, doctor, validate, process, export, ...)
  mcp/      MCP connector for any agent
  testkit/  dev-only test helpers: generated fixtures, non-ASCII temp directories
  e2e/      end-to-end tests (Playwright)
agent-kit/
  claude-code/   Claude Code plugin (commands and skills)
  AGENTS.md      the same instructions for other agents
docs/
examples/sample-library/   only the maintainer's own or freely licensed media
```

Planned building blocks (each confirmed or replaced when its milestone starts): React + Vite for the interface; Hono for the local server; zod for validation; Playwright for page capture; sharp (WebP) and `ffmpeg-static` for media; Vitest and Playwright for tests; GitHub Actions on Linux, Windows and macOS; a pinned Node LTS.

### Compiler configuration

- `tsconfig.base.json` holds the shared options: `target` and `lib` `es2025`, `module` `nodenext`, `types: []`, `strict`, `noUncheckedIndexedAccess`, `noImplicitOverride`, `verbatimModuleSyntax`, `isolatedModules`, `erasableSyntaxOnly`, `forceConsistentCasingInFileNames`, `skipLibCheck`, `composite`, `declaration`, `declarationMap`, `sourceMap`. Paths use `${configDir}`, so every package compiles `src/` to `dist/` (`e2e` is the exception: it compiles `tests/` and its Playwright config, declarations only) and keeps its `.tsbuildinfo` inside `dist/` (deleting `dist/` forces a rebuild).
- Each package's `tsconfig.json` extends the base and adds only `types` and `references`, plus an `exclude` for `*.test.ts` when it has unit tests (type-checked by its `tsconfig.test.json`, §15). Node packages set `types: ["node"]` and write relative imports with the `.js` extension. `web` sets `module` `esnext`, `moduleResolution` `bundler`, `jsx` `react-jsx`, `lib` `["es2025", "dom"]`, emits declarations only (Vite produces the bundle) and writes relative imports without an extension.
- The root `tsconfig.json` is a solution file (`files: []`, references to every package and to the test configs) for editors and `tsc -b` from the root.
- The configuration avoids every option that TypeScript 6.0 deprecates, so moving to TypeScript 7 is a version bump (checked: 7.0.2 builds it unchanged).

### Build

- Each package's `build` script is `tsc -b`. `pnpm -r build` runs them in dependency order; `pnpm build` at the root does the same, and `pnpm clean` runs `tsc -b --clean`.
- `web`'s build is `tsc -b && vite build`: `tsc` type-checks and emits declarations, Vite writes the app to `packages/web/dist/app`. `pnpm --filter @tastelib/web dev` starts the Vite dev server.
- Scripts in any `package.json` call only cross-platform programs (`tsc`, `pnpm`, `vitest`, `playwright`, later `vite`). No shell built-ins (`rm`, `cp`, `mkdir -p`), no inline environment variables (`FOO=1 cmd`), no quoting or globbing that only a POSIX shell understands. A step that needs more is a Node script.

### Check command, lint and format

- `pnpm check` is the single gate, run locally, by agents (loop step 5) and in CI: `pnpm lint && pnpm format:check && pnpm typecheck && pnpm test && pnpm build`. It stops at the first failure and exits non-zero.
- Biome does both linting (`recommended` rules; `pnpm lint` fails on warnings too) and formatting (2 spaces, double quotes, semicolons, 100 columns, LF). `pnpm format` rewrites files; `pnpm lint` and `pnpm format:check` only report.
- Biome is limited to code and data files (`.ts`, `.tsx`, `.js`, `.mjs`, `.json`), listed in `biome.json`. Markdown and YAML are not touched: it would reflow tables and prose in the design documents. It honors `.gitignore`.
- `pnpm typecheck` is `tsc -b`. `pnpm test` runs each package's `test` script when it has one (`pnpm -r --if-present test`); the test layout is in §15.
- `pnpm install` runs `prepare`, which runs `scripts/setup-hooks.mjs`: it sets `core.hooksPath` to `.githooks` in a Git checkout and does nothing elsewhere. New clones get the hooks without a manual step.
- CI runs `pnpm check`, then the end-to-end tests (`pnpm test:e2e:install`, `pnpm test:e2e`), on `ubuntu-latest`, `windows-latest` and `macos-latest` with the Node version from `.nvmrc` and the pnpm version from `packageManager`. The pnpm store is cached through `pnpm/action-setup` (`cache: true`); actions are pinned to full commit SHAs and `zizmor` audits the workflows.
- Dependabot watches the npm ecosystem weekly with a 7-day cooldown, groups development dependencies into one PR and uses the `chore(deps)` prefix.

### Core modules and API

`packages/core/src/` is split by what a module may touch. Pure modules run unchanged in Node and in a browser, so `web` can use them from M2; everything that touches the operating system lives in `node/`.

| Folder or file | Holds | Kind |
| --- | --- | --- |
| `json/` | the strict reader on bytes (`read.ts`, §4 "Reading library files"), the canonical serializer (`canonical.ts`), JSON Pointer helpers | pure |
| `schemas/v<N>/` | the frozen zod schemas of format version N (format-spec §15.4): `shared.ts` for §4 of the spec, one module per file type, and `set.ts`, the schema set of the version | pure |
| `format.ts` | `CURRENT_FORMAT_VERSION` and the format registry: for each version its schema set, its folder layout (which relative paths are which file type) and its step to the next version | pure |
| `validation/` | the `Issue` type and the table of codes with their severities, the mapping from zod issues to issues with pointers and English messages, the checks within one file, the cross-file checks over a set of parsed files, and the report of format-spec §16.3 | pure |
| `ids/` | random identifiers, sequential numbers, slugs | pure |
| `model/` | derived values: effective value (format-spec §13.3), derived state (§7.7), region rounding and timestamp bounds (§4 "Writing library files") | pure |
| `library-index/` | the index, built from parsed files (§4 "Index") | pure |
| `changes/` | write plans: what a plan changes, which links are new, link removal for deletions | pure |
| `migrations/` | the step modules `v<N>-to-v<N+1>.ts` (format-spec §15.4) | pure |
| `node/` | the file-system adapter, reading files, opening and refreshing a library, the atomic replace, the write pipeline and gate, media checks, the migration runner and its recovery, the process probe, and the per-machine config (`config.ts` moves here from `src/`) | Node |
| `index.ts` | the Node entry, `@tastelib/core`: everything | Node |
| `browser.ts` | the browser entry, `@tastelib/core/browser` (`exports["./browser"]`): re-exports pure modules only. It arrives with the first pure module; `web` imports it from M2 | pure |

- **Pure** means: imports only `zod` and other pure modules through relative paths, never an `index.js` or `browser.js` (the two entries are the only barrel files in `src/`), and uses no Node-only global (`process`, `Buffer`, `setImmediate`, `clearImmediate`, `require`, `module`, `__dirname`, `__filename`) and no global object (`globalThis`, `global`, `self`, `window`), so every global is named directly where the rule can see it. Globals that Node and browsers share (`TextDecoder`, `TextEncoder`, `crypto.getRandomValues`, `URL`, `structuredClone`) are allowed and used by their bare names. SHA-256 (for `inputSha256` and `proposal-stale`) is passed in by the caller as a synchronous function (`node:crypto` in `node/`), because the browser's Web Crypto `digest` is asynchronous.
- **Checked by a lint rule**, so `pnpm lint` fails at the offending line. The root `biome.json` has an `overrides` entry for `packages/core/src/**` except `node/**`, `index.ts` and `*.test.ts` that turns on `correctness/noNodejsModules`, `style/noRestrictedGlobals` (the globals and global objects above) and `style/noRestrictedImports` with two pattern groups: an allowlist (`**` except `zod`, `./**` and `../**`) and a denylist (`**/node/**`, `**/test/**`, `**/index.js`, `**/browser.js`). Pure is the default: a new folder is pure unless it is under `node/`. The rules were checked on Biome 2.6.4: a `node:` or bare built-in import, a third-party import, an import of `node/`, of test code or of an entry, `process`, `Buffer`, `globalThis.process`, `globalThis["Buffer"]` (through the ban on `globalThis`) and `self` are each reported, while `node/` and test files are not touched. It is a lint rule, not a sandbox: code written to get around it, such as `Function("return this")()`, is not reported, so code review still watches pure modules for it.
- **Test-only code is never under `src/`** (§15 "Core test approach"), and the build's `rootDir` is `src/`, so nothing test-only can reach `dist/`.

**Public API for M2 and M3** (names are indicative; the shapes are the decision):

- `openLibrary(root, options)` reads every library file once and returns either `{ ok: true, library }` or `{ ok: false, code, message }` with `code` `not-a-library` (no `library.json`) or `unreadable-folder`; the CLI turns those into exit 2 (format-spec §16.1). `library` is a handle that long-running processes (the M2 server, the M3 MCP connector) keep open.
- `library.snapshot()` returns an immutable **snapshot**, refreshed first (§4 "Index"): `formatVersion` (of `library.json`, or `null`), `files` (a map sorted by relative path; for each file its kind, its exact bytes, its `formatVersion`, its status `valid`, `invalid`, `newer` or `unreadable`, its parsed value at the current version when valid, migrated in memory if older, and its own issues), `issues` (the whole report, sorted as in format-spec §16.3) and `index`. A refresh reuses every unchanged file's entry, so snapshots share structure and cost little to keep.
- `checkMedia(snapshot, mediaRoot, { checksums })` returns the media issues separately, so refreshing a snapshot never hashes media.
- `library.write(build, options)` runs the write pipeline (§4 "Writing library files"). `build` receives the fresh, gated snapshot and returns a **plan**: `{ changes, skipped }`. `changes` is an ordered list of file changes (`{ path, next }`, `next` being the new value or `null` for a deletion), the first one being the primary change (format-spec §5); `skipped` lists the files the operation chose to leave alone, each `{ path, reason }` (for example link removal skipping a file with errors, §4 "Links to files with errors"), and is passed through unchanged to the result. Because the plan is built after the gate, a write that first migrates the library builds its plan on the migrated files. Writes through one handle run one at a time, in order, so two requests in one process never race each other; across processes the optimistic check decides.
- **Issues** are plain data in the exact shape of format-spec §16.3: `{ severity, code, file, pointer, message }`, with `file` relative to the library with `/` (or `media:…`, or `null`), never absolute. The severity of a code is always the one in format-spec §16.2, also in a refusal.
- **Errors that are not validation issues** never become an `Issue`, because format-spec §16.2 is the contract of the validation report and gains no code without a new format version. They are returned as results with their own stable codes: `not-a-library` and `unreadable-folder` (open) and `io-error` (a file could not be read back, written, flushed, renamed or removed during a write: `{ code: "io-error", operation, file, errno, message }`, with `file` relative to the library). The command line adds them to its list of codes. A read failure while opening is the issue `unreadable-file`, as format-spec §16.2 says. Expected failures are never thrown; a thrown exception means a bug.
- **A write result** has a `status` and, whatever the status, `notices` (empty when there are none), for example `{ code: "migrated", from, to }`: `migrated` is in `notices` exactly when the gate's migration reached the manifest marked `done` (format-spec §15.3 step 6), whatever the final status, including refused, unchanged or failed, because the library was then migrated on disk; a migration that was undone by the runner's own cleanup, or that never wrote, gives no `migrated` notice. The statuses are `written` (with the files written and `skipped`, taken from the plan's `skipped`), `unchanged` (the plan changes no file, so nothing is written and no `updatedAt` moves), `refused` (a check stopped it: `issues`, for example validation errors, a new `dangling-link`, `write-conflict`, `newer-format`, a migration that cannot run, later `not-allowed`) or `failed` (a `failure` with its code: `io-error`, or `not-a-library` or `unreadable-folder` when the folder stopped being a readable library after it was opened). `refused` and `failed` also list the files written and not written, which are both non-empty only when a multi-file write stopped after its first rename (format-spec §5).


## 4. Library, media and configuration

- A **library** is a folder (usually its own private Git repository) holding the data files described in [format-spec.md](format-spec.md).
- **Media** (images, full-page captures, videos, frames) lives in a separate **media folder**, outside any Git repository. It can be any folder, including one kept in sync by a file-sync service; the tool never depends on a particular service.
- The tool refuses a media folder that sits inside a Git working tree, and `tastelib doctor` checks it.
- Media that a library references but that has not arrived yet (for example, still syncing from another computer) is shown as **awaiting sync**, never as an error.
- **Per-machine configuration** (where the library and the media folder are on this computer) lives outside the library: `~/.config/tastelib/config.json` on Linux and macOS, `%APPDATA%\tastelib\config.json` on Windows. It is never committed. It also holds the other settings that belong to one computer: the interface language (§12) and where packs are exported (§10). The library itself holds no machine path.
- **The config file** is JSON with `version` (`1`) and these optional fields: `libraryPath`, `mediaPath`, `packsExportPath` (absolute paths in the form of the operating system that reads the file, with no `.` or `..` segments), and `language` (`en` or `pt-BR`). Unknown fields are refused. A missing file means the defaults (`{ "version": 1 }`). On Linux and macOS, `$XDG_CONFIG_HOME` is used when it is an absolute path, otherwise `~/.config`. A file over 1 MiB, or one that is not a regular file, is not read (a symbolic link to a regular file is followed, and the size is checked on the file it points to). Every error, including a failed write, is a `ConfigError` that names the config file and, when it concerns one, the field. It is written atomically (temporary file in the same folder, `fsync`, rename), and a write that fails validation leaves the old file untouched. A `mediaPath` inside a Git working tree (a `.git` folder or file in the path or any parent, after resolving symbolic links) is refused when the config is written.
- A media folder belongs to one library: it holds a marker file with the library's id (`tastelib-media.json`), so attaching the wrong folder is detected.
- Every write goes through `tastelib`, is validated first and replaces the file atomically (temporary file in the same folder, then rename). The exact rules, including how `tastelib validate` reports errors and warnings, are in [format-spec.md](format-spec.md) §16.
- **Concurrent writers** (the app and an agent at the same time) are handled by an optimistic check: just before the rename, the writer reads the file again and compares it with the bytes it started from; if they differ it refuses with `write-conflict`, and the caller reads again and retries (format-spec §5). There is no lock file. If real use shows conflicts the check cannot catch, M1 or later adds a lock. A write that touches several files (a deletion that removes links, a merge) is not atomic as a whole: `tastelib` checks every file before the first rename, writes the user's decision first and removes links after, and reports which files were written if it stops partway, so a partial stop leaves at worst dangling links, never a lost decision (format-spec §5).
- **Timestamps** are UTC. Because clocks on two computers may disagree, a writer sets `updatedAt` and `reviewedAt` to the later of now and their lower bound (format-spec §4.1), so a skewed clock never makes a write fail.
- **Format versions.** Read-only commands migrate an older library in memory only. Before its first write to an older library, or to a library whose files have mixed versions, `tastelib` migrates it on disk automatically and says so; `tastelib migrate` (with `--dry-run`) does it on request. A migration is validated completely before anything is written, keeps a backup until it finishes, and writes `library.json` last. The migrating process claims the backup folder with a non-recursive `mkdir` (only one can succeed), writes `owner.json` with its process id and host name before copying anything, copies the files into it atomically, and only then writes a manifest marked `in-progress`; the manifest is marked `done` after `library.json` is written, and only then is the backup deleted, `owner.json` last. The copies, `owner.json`, both manifest writes, every library file the migration writes and every file a recovery restores are flushed to disk (`fsync` of the file before its rename, and of each touched folder after it where the operating system allows it) before the next step, so a power cut can neither leave a backup that recovery would trust but that is empty, nor a manifest marked `done` over library files that never reached the disk. No other write runs while a backup exists: with no owner file yet, an owner on another host, a live owner, or an unreadable manifest, the write fails with `write-conflict` (retry later) and the backup is kept; with the owner gone, a backup marked `done` or with no manifest (the copy never finished; the originals are untouched) is deleted, and one `in-progress` is restored and the migration runs again (format-spec §15.3). Several processes that find the same abandoned backup race for it by renaming `owner.json` to a unique name. A rename that succeeds wins only if the renamed file holds exactly the bytes of the `owner.json` the recoverer judged gone; otherwise it has taken the live claim of a recoverer that already won, puts it back with an exclusive create (`wx`) and checks again. The winner creates its own `owner.json` exclusively too, so it can never replace someone else's, deletes the renamed file, and recovers; the others check again from the start. A restore during recovery overwrites files that changed after the interruption (for example through a `git pull`); their newer versions remain in Git history. When a backup stays stuck (a reused process id, a crash right after the claim, just before the folder is removed, or by a takeover winner before it created its new `owner.json`, an unreadable manifest, or a computer that was renamed and now looks like another host), `tastelib doctor` reports it, and `tastelib doctor --resolve-migration` shows what it holds and, after the user confirms, restores or deletes it. Before a restore it warns that restoring overwrites any of those files that changed since the interruption, for example through a `git pull`. Unlike the rest of `.tastelib/`, the backup folder must never be deleted by hand or by cleaning tools such as `git clean -X` while a migration is in progress or interrupted (format-spec §5). The version in `library.json` does not decide this, because a library with mixed file versions migrates while `library.json` is already current. There are no down-migrations; Git history is the way back. The media folder's marker has its own version: it is migrated on disk when the media folder is next attached or written to, and in memory only by read-only commands.

How `core` builds this is below; its modules and API are in §3 "Core modules and API".

### Reading library files

- **I/O.** A file is read through one handle (size check and read on the same handle, as `readConfig` does): over 8 MiB gives `file-too-large` and is not parsed; a read error gives `unreadable-file`; a file that disappears between the listing and the read is treated as deleted. Opening a library keeps up to 16 reads in flight (2.5 times faster than one at a time in the probe), and results are ordered by path, never by completion. The exact bytes are kept in the snapshot for the optimistic write check (format-spec §5).
- **The strict reader** is a pure function from bytes to a value or issues, and is original code: an RFC 8259 parser with an explicit stack, never recursion.
  - Decoding uses `TextDecoder("utf-8", { fatal: true, ignoreBOM: true })`; a decoding failure gives `invalid-encoding` (pointer `null`). A leading U+FEFF is skipped and recorded, and so are CR characters, so a `not-canonical` message can say why.
  - Duplicate keys are found while parsing, comparing the decoded keys (so `"a"` and `"\u0061"` are the same key), and give `duplicate-key` at the pointer of the repeated key (`/pins/0/note`). A string or key that decodes to a lone surrogate (`!isWellFormed()`) gives `invalid-encoding` at its pointer. The reader goes on after these two, so every one is reported, and stops at the first syntax error, which gives `invalid-json` (pointer `null`, with line and column in the message).
  - Numbers are checked against the RFC 8259 grammar and converted with `Number()`, the same correctly rounded conversion as `JSON.parse`. Range rules (integers up to 2^53 − 1, finite proportions) belong to the schemas.
  - A key named `__proto__` becomes an own property, as with `JSON.parse`, so the strict schemas report it as an unknown field and no prototype is touched.
  - **Nesting is limited to 64 levels** of objects and arrays; deeper input gives `invalid-json` ("nested deeper than 64 levels") and is never thrown. RFC 8259 §9 allows a parser to limit nesting depth, so this is still plain JSON and needs no new code. The deepest v1 file has 5 levels (a reference's `interpretations` → piece → `proposal` → `vocabulary`). The limit is needed whichever parser is used: `JSON.parse` itself survived 5 million levels in the probe, but zod and every recursive walk do not (zod threw `RangeError` at 100 000 levels; a plain recursive JavaScript function overflows at about 12 500 frames).
- **Validation** of a parsed file runs its version's schema and the rules within the file, then the cross-file checks run over all parsed files. A file with any error is `invalid`: its value is not used by the index or by other files' checks.

### Writing library files

Every write runs these layers in order. Each layer either passes or ends the write with a result (§3); nothing of the plan touches the disk before layer 8. The gate's recovery and migration (layer 1) are the exception: they write before the plan exists.

1. **Gate** (below): refresh the snapshot, then check the migration backup, newer files and older or mixed versions.
2. **Plan:** `build` returns the file changes from the gated snapshot. A plan may not replace or delete a file whose status is not `valid` (refused with that file's issues): a file with errors may hold the user's words in a form the tool cannot read, for example after a hand-resolved merge, and only the user repairs it, by hand or with a later repair command.
3. **Authorize** (M3): agent writes are checked against the allowlist (format-spec §13.1) by comparing old and new values; outside it gives `not-allowed`. User writes pass.
4. **Validate** each changed file: the schema and every rule within the file. Then, on a view of the library with the plan applied, the **new links**. A link is new unless the same holder already linked to the same target in the old value: the holder is the entry with the same id (a term, guardrail, statement or direction) or, for links outside entries, the same field of the same file (a family's `members`, a reference's `result`). So a new term that links to a piece that another term already links to is still a new link. A new link must resolve, otherwise the write is refused with `dangling-link` (severity `warning`, as in format-spec §16.2, but listed among the issues that refused the write). Links that were already dangling are kept. A new link into a file that exists but is not `valid` cannot be checked and is refused the same way, with a message naming that file. Warnings in the new value (`proposal-stale`, `duplicate-term`) do not block.
5. **Canonicalize** the values: round proportions (below), sort lists and order keys (zod's output follows the schema's key order; `interpretations` keys are sorted by piece number in code, because `z.record` keeps input order).
6. **Timestamps:** the pipeline sets every `updatedAt` itself, so no operation can forget one; operations leave the old `updatedAt` in place (or `createdAt`, for something new). For each file in the plan, the canonical new value is compared with the canonical form of the old value, with every `updatedAt` field set aside. If no file differs, the write ends as `unchanged`, writes nothing and moves no timestamp (so a valid file that is merely not canonical is not rewritten by a write that changes nothing in it). A file that differs gets `updatedAt` = the later of now and its `createdAt`; entries with their own `updatedAt` (terms, guardrails, statements, directions) are compared by id the same way and set the same way. The same helper in `model/` gives `reviewedAt` the later of now and `proposedAt` in the review operations (format-spec §4.1). The clock is a function passed in options (`() => Date`, default the system clock), so tests fix time and skew.
7. **Serialize:** the final value, timestamps included, is validated again as an internal assertion (a failure is a bug and throws), then written as `JSON.stringify(value, null, 2)` plus LF.
8. **Replace** each file, the primary change first (format-spec §5):
   - First, check every target against its snapshot bytes (or its absence) before anything touches the disk.
   - Then create the missing folders (`references/`, `families/`, `projects/<slug>/`, "created when first needed", format-spec §5) one level at a time with a non-recursive `mkdir`, remembering which ones this write created.
   - For each file: write a temporary file `.<name>.tmp-<8 Crockford characters>` in the same folder (created exclusively, `wx`), `fsync` it and close it. Just before the rename, and again before each Windows retry (below), read the target again and compare it, and `lstat` `.tastelib/migration-backup/` again: a different target, or a backup that appeared since the gate (another process started a migration), ends the write with `write-conflict` and deletes the temporary file. Then rename it over the target. A deletion uses the same checks before `unlink`.
   - If the write ends `refused` or `failed`, every folder this write created and left empty is removed again (non-recursive `rmdir`; a folder that another writer has filled meanwhile stays), so a refusal leaves the library as it was, folders included.

   What remains is the short window between the last re-read and the rename, which format-spec §5 accepts.
9. **Update** the snapshot from the bytes written. Their fingerprints are marked unsettled (§4 "Index"), so the next refresh reads them back once instead of trusting a `stat` that another writer may have raced.

**Cleanup only on result paths.** On-disk cleanup (deleting a temporary file, removing a folder this write created, a migration cleaning up after itself) runs only where a recognized failure is turned into a result: an error from the file system with an `errno` code, or a failed check. It never runs in a `finally` block or in a catch that rethrows. Any other exception (a bug, or the tests' `SimulatedCrash`, §15 "Core test approach") propagates with nothing cleaned up, exactly like a process that dies at that point, so the crash tests see what a real crash leaves. Closing file handles in `finally` is allowed; it changes nothing on disk.

**Proportions.** Regions are rounded per axis in integer millionths, on values that already passed validation (rounding is not a repair, so a negative width is still refused): `P = round(x × 10^6)`, `S = round(w × 10^6)`; then `S = max(S, 1)` (a tiny width must not become 0), `P = min(P, 10^6 − 1)`, and if `P + S > 10^6` then `S = 10^6 − P` (the clamp keeps the edge); `x = P / 10^6`, `w = S / 10^6`; the same for `y` and `h`. Rounding each value on its own fails twice over: `x = 0.1234565, w = 0.8765435` (sum 1) gives `x + w = 1.000001`, beyond the 1e-9 tolerance (format-spec §7.3), and `w = 4e-7` becomes `0`. Checked on 2 million random valid regions, including regions touching the edge, within the tolerance beyond it, and tiny at the far edge: none became invalid, the rule is idempotent, a valid region whose four values all have at most 6 decimals is never changed (each axis is rounded on its own, and a valid axis whose two values have at most 6 decimals is left as it is; so other writers that keep at most 6 decimals stay canonical), no value moves by more than 1e-6, and `JSON.stringify` of `k / 10^6` never prints more than 6 decimals or an exponent. This is a rounding rule within format-spec §3.3, not a format change. `not-canonical` compares a valid file's bytes with the canonical form of its value, rounding included.

**Durability.** Every library write `fsync`s its temporary file before the rename, on every platform. Without it, a power cut after the rename can leave the target empty or truncated on some file systems and mount options (the rename reaches the disk before the data), which would lose the user's words; the cost is one flush per file, while writes come at the pace of a person or an agent, and the config writer already does it. The folder is flushed after the rename (and after a deletion) only in **durable mode**, for the files recovery depends on (format-spec §5, §15.3), and never on Windows: without that flush a power cut can undo the rename, which leaves the previous complete file, a lost recent edit but not a broken file, and only matters where recovery depends on the order of steps. On macOS, Node's `FileHandle.sync()` issues `F_FULLFSYNC` through libuv, a real flush of the drive cache, which is slower than on Linux; a migration that rewrites thousands of files therefore spends noticeable time flushing, so the runner flushes only what format-spec §15.3 requires.

**Windows renames and deletions.** On Windows, a `rename` or `unlink` that fails with `EPERM`, `EACCES` or `EBUSY` (a file held open by an antivirus, a sync client, an indexer or an editor) is retried until 2 seconds have passed since the first failure, waiting 10 ms before the first retry and doubling the wait up to 250 ms. Before each retry the optimistic check is repeated: if the target changed meanwhile, the write ends with `write-conflict` and the temporary file is deleted. When the time is up, the write ends with `io-error` naming the operation and the error code, and the temporary file is deleted. If that fails too, the temporary file stays: inside `references/`, `families/` and `projects/`, `validate` reports it as `leftover-temp-file`; at the top level of the library (the temporary file of `library.json`, `glossary.json`, `guardrails.json` or `taste-profile.json`), format-spec §5 ignores other files and `validate` does not report it, so `tastelib doctor` lists it instead (its checks are specified with the command line). On Linux and macOS these errors are real permission problems and are not retried. The platform is an option of the file-system adapter, so the retry path is tested on every CI system. `graceful-fs` retries the same codes for up to 60 seconds, which suits package installs but would freeze an interactive write for a minute.

### Write gate

Before the plan is built, every write checks, in order:

1. **Refresh** the snapshot (§4 "Index"). This is how a write learns the state of the whole library without reading every file each time: a long-running process (the M2 server, the MCP connector) keeps its snapshot and refreshes it with a `stat` scan, re-reading only files that changed; a one-shot CLI command reads every file once when it opens the library and writes with that snapshot. The version summary in the index (each file's `formatVersion` and status) answers the next three checks without another read.
2. **Migration backup:** `lstat` of `.tastelib/migration-backup/` on every write, never cached, and again before each rename and each Windows retry (layer 8 above). While it exists, recovery runs first (format-spec §15.3). Until recovery is built, every write gets `write-conflict`.
3. **`library.json`:** missing (or the folder can no longer be read), the write ends `failed` with the same `not-a-library` (or `unreadable-folder`) failure that `openLibrary` returns; present but not `valid`, it is `refused` with that file's issues, because the library's version is then unknown.
4. **A `newer-format` file anywhere** in the library (format-spec §15.1): refused, with one `newer-format` issue per newer file.
5. **An older or mixed library:** migrated on disk (format-spec §15.2–§15.3), then the snapshot is refreshed and the write goes on with a `migrated` notice, which stays in the result whatever happens to the plan afterwards (§3). A migration that cannot run (a file with errors at step 1, or errors left after the steps at step 3 of format-spec §15.3) writes nothing, and the write is `refused` with the issues of the files that block it; one that fails after its claim ends as described in "Migration runner failures" below. At version 1 no library can be older or mixed, so this path first runs with the test-only step (§15 "Core test approach").

Writes to the media folder have their own guard on the marker (format-spec §6.1, §15.1).

### Migration runner failures

- **The backup copies** (format-spec §15.3 step 4) are made from the files on disk, read again after the claim, never from the bytes held in memory since step 1. Each one is compared with its step-1 bytes; a difference means something changed the file between step 1 and the re-read after the claim, so the runner stops on the path before the manifest exists: it deletes the backup in the order of step 7 (`owner.json` last), and the write is `refused` with `write-conflict` naming that file. No library file has been written at that point, and a backup never holds bytes that were no longer on disk.
- **The runner's own writes** (format-spec §15.3 step 5, and the deletions there) use the same replace primitive, with the bytes it read at step 1 as the expected bytes (absent for added files), and without the backup check, since the backup is its own. Other `tastelib` writers are kept out by the backup, so a mismatch means something outside `tastelib` (a `git pull`, an editor) changed the file during the migration. The runner then stops and cleans up as below, and the write is `refused` with `write-conflict` naming that file; the next write reads everything again and migrates from there. Only the window between a re-read and its rename remains, as for every write.
- **A runner that fails after its claim cleans up its own backup before it returns**, as the owner finishing its own migration (format-spec §15.3 keeps *other* writers out while the owner is alive; the owner itself may finish): an I/O error or a conflict before the manifest exists deletes the backup in the order of step 7 (`owner.json` last), because no library file was written yet; with the manifest `in-progress`, it undoes only what this run did, from the list it keeps in memory: each file it already replaced or deleted is restored from the backup, checked first against the bytes the runner wrote (or against its absence, for a deletion), and each added file it created is removed, checked the same way; every file it had not reached yet, including the one that conflicted, is left untouched. Restores and removals are durable as in recovery case 7. Then it deletes the backup; with the manifest `done`, it deletes the backup. The write then ends `failed` (`io-error`) or `refused` (`write-conflict`), and the library is as it was before the migration (or migrated, if `done` was reached). This runs only on these result paths (§4 "Writing library files", "Cleanup only on result paths").
- **If that cleanup fails too** (the disk is still failing, or a restore meets a file changed meanwhile), the backup stays, with this process as its live owner. A file whose bytes are neither those the runner wrote nor the backup's (something else changed it meanwhile) is left as it is. Other processes treat it as live (case 3) until this process ends, as format-spec §15.3 requires. So that a long-running process (the M2 server, the MCP connector) does not block its own writes for as long as it runs, it remembers, in memory, the backup it failed to clean up and the exact bytes of the `owner.json` it wrote; before its next write it resumes that cleanup as the owner, but only if `owner.json` still holds exactly those bytes. A resumed cleanup accepts, for each file of its list, exactly two states: a file the runner replaced holds the runner's bytes (restore it from the backup) or the backup's bytes (already restored); a file the runner deleted is absent (restore it from the backup) or holds the backup's bytes (already restored); a file the runner added holds the runner's bytes (remove it) or is absent (already removed); a file in any other state stops the resumed cleanup, the backup stays, the write is `refused` with `write-conflict`, and the user resolves it with `tastelib doctor --resolve-migration`. Otherwise, and once the process has ended, the recovery cases of format-spec §15.3 apply as usual, and `tastelib doctor` reports a backup that stays stuck.

### Links to files with errors

A cross-file link resolves if its target file is `valid` and holds the target (the reference and its piece `p0` or a pin; the family; the project and its direction; the guardrail). It is dangling if the target file is absent, or `valid` without the target. A link into a file that exists but is not `valid` (`invalid`, `unreadable` or `newer`) is **unresolved**: `validate` reports no `dangling-link` for it, because whether the target exists cannot be known and the broken file already has its own error, the one to fix; the index counts it for nothing (a broken family gives its pieces no family); a write that adds such a link is refused (layer 4 above); and link removal after a deletion skips files that are not `valid` and still writes the deletion, and the `written` result lists each skipped file in `skipped` with the reason (`{ path, reason: "invalid" | "unreadable" | "newer" }`), so an unrelated broken file never blocks the user's decision. A link that is still there shows up as `dangling-link` once that file is repaired.

### Index

The index is derived data, kept **in memory only**, inside the snapshot; nothing is cached under `.tastelib/`, so deleting `.tastelib/` (outside an interrupted migration) can never make it wrong.

- **What it holds** (M2–M4): every file's kind, fingerprint, `formatVersion` and status, and a version summary (the library's version, the versions present, whether any file is newer, whether versions are mixed); every reference with its pieces (`p0` and its pins), its derived state (inbox, processed, reviewed, format-spec §7.7, a rejected interpretation counting as reviewed, §13.3) and its `result` link; the families of each piece, derived from `members`: a family whose description has no effective value, or a rejected link, gives nothing, and a `to-review` description or link gives a tentative family; the existence sets the dangling checks use (references and their pieces, families, projects and their directions, guardrails); and backlinks: for each link target, every `(file, pointer)` that links to it, for link removal and for showing where something is used. Each later milestone adds the views it needs (the review queue in M3, browsing in M4) as pure functions of the parsed files.
- **How it is built.** Work per file (read, parse, validate, migrate in memory) is cached by fingerprint and redone only for changed files. Everything library-wide (cross-file checks, derived states, families, backlinks) is recomputed from the parsed files after every change, since it costs about 10 ms for 5000 references. So an updated index is always a fresh rebuild from the same parsed files, and there is no incremental update that could drift.
- **Freshness.** Before any answer, and before every write, a refresh lists the format folders and `stat`s every file. The fingerprint is `(size, mtime, ctime, inode)` from `stat` with `bigint: true` (nanoseconds where the file system has them). A listed name that is new, gone or has a different fingerprint is re-read. A file is kept **unsettled** when `0 ≤ statTime − mtime < 3 s`, `statTime` being the system clock when it was stat'd (an `mtime` in the future, for example from a sync tool that keeps another computer's times, does not count): the next refresh reads it again and compares bytes, whatever its fingerprint, because a second change within the file system's timestamp resolution (2 seconds on FAT) could keep size and `mtime`. A request is answered from a refresh that started after the request arrived; requests that arrive together share one refresh.
- **No `fs.watch`** in M1. Node documents it as "not 100% consistent across platforms" and unreliable on network file systems and in virtual machines; a sync folder or a `git pull` would be missed silently. The M2 server may add it only as a hint to push "library changed" to the interface, never as the reason to skip a refresh.
- **Performance budget**, checked by a test on Linux, Windows and macOS CI, on a library generated at test time with a fixed seed: 5000 references (1–2 media items, 0–5 pins, about 60% of pieces interpreted, about 3.4 KB per file), 50 families of 100 members, 300 glossary terms and one project, about 17 MB in all:
  - opening it (read, parse, validate every file, cross-file checks, index) **under 5 seconds**;
  - refreshing it when nothing changed **under 0.5 seconds**, and when one reference changed, with the index updated, **under 0.5 seconds**;
  - one single-file write on the open library, gate and `fsync` included, **under 1 second**.

  A throwaway probe on a desktop, with a warm cache, measured about 0.6 s to open (listing 4 ms, reading with 16 concurrent reads 115 ms, decoding 25 ms, the prototype strict parser 180 ms, a v1-like zod schema 180 ms, the canonical check 65 ms, the index 9 ms) and 35 ms for a refresh. The budget leaves about 8 times the measured open and 14 times the measured refresh for slower CI runners and Windows file access, which was not measured. Reading every file once per CLI command is acceptable at this size. If the budget fails, or the M2 checkpoint shows CLI commands are too slow, the first remedy is a cache under `.tastelib/` keyed by the same fingerprints (still disposable), decided then.

## 5. Capture

Capture happens on the computer, in the app, by pasting or dropping:

- **Screenshots and images**, stored compressed (WebP).
- **Page URLs**, captured as a full-page image by a headless browser, on the user's request only.
- **Videos and GIFs**, for motion; stored compressed, with frames extracted for pinning.

New captures land in an **inbox** until processed.

**(to specify in M2)** size limits, compression settings, capture timeouts, frame extraction.

## 6. Notes and pins

- Each reference has a **free-text note** in the user's own words.
- **Pins** are boxes drawn on an area of an image or of a video frame. Each pin is a **piece** with its own note. The whole-reference note counts as a piece covering the whole image.
- A pin is **positive** (take this) or **negative** (not this). Negative pins are the source of **guardrails**. There are no whole-image anti-references.
- Regions are stored as proportions (0–1) of the media size, so they survive resizing.
- The whole-reference note is piece `p0`; pins are `p1`, `p2`… A pin on a video sits on one of its extracted frames. Pieces are addressed across the library as `<ref-id>#p<n>`.
- The app stores notes exactly as typed; the only change is that line breaks are stored as `\n`. A note that breaks a rule (for example, a control character) is refused with a message, never silently altered.

## 7. Interpretation and review

- Interpretation runs in **batches through an agent** ("process my new references"). For each piece, the agent proposes vocabulary, keywords, screen types, components, design aspects and, for negative pins, a guardrail.
- Everything the agent writes is marked **`to-review`**. In the app, a review queue offers **Accept**, **Correct** or **Reject**. A correction is the user's complete version, stored next to the original proposal, which is never modified after review. Rejected proposals are kept, so agents see what the user refused and do not propose it again.
- The user's own words are never altered.
- Agent writes are an allowlist (format-spec §13.1): through `tastelib` (CLI or MCP), an agent can only add proposals marked `to-review` (piece interpretations, new families, glossary terms, guardrails, profile statements, directions, an intent with its discarded list, and pieces proposed for a family), set the links of an entry it created while that entry is still `to-review`, and replace an agent proposal while it is still `to-review`, whoever proposed it (`proposedBy` is updated). Everything else is refused with `not-allowed`: references (capture, media, pins, notes), names, user-authored values, corrections, review statuses, links of reviewed entries, reopening, deleting and merging. Those are the user's, in the app.
- While a proposal is `to-review`, an agent may replace it. Once reviewed, an agent cannot replace or delete it; the user can reopen it, and only then can an agent propose again.
- `tastelib` records a fingerprint of the note each proposal was based on. If the user edits the note later, the proposal is flagged as stale and the app offers to reopen it.
- Until it is reviewed, a proposal is **tentative**: shown as such and not exported as the user's taste unless the user chooses to.
- Who writes which field, and the effective value consumers use, are specified in [format-spec.md](format-spec.md) §13.

## 8. Organization and taste tools

- **Aesthetic families emerge** from the collection. The agent proposes a name, a meaning and a vocabulary; the user accepts, renames or merges.
- Browsing also works by **screen or page type**, **component** and **design aspect**.
- Taste tools: **family pages**, a **taste profile** (likes, rejections, contradictions), a **vocabulary glossary**, and **side-by-side comparison**.
- A family's pieces are listed in the family; the agent proposes pieces, and the user accepts or rejects each one. A family's slug is fixed at creation; renaming changes its name only. Merging moves the pieces and replaces links to the merged family.
- The taste profile is stored as separate statements, each reviewed like any proposal. Its Markdown view is rendered when needed, not stored.
- Guardrails are proposed from negative pins into one list of candidates; a candidate becomes approved when the user accepts or corrects it.

**(to specify in M4)**

## 9. Project spaces

- A project space pulls pieces from the library and adds its own layer: intent, directions, packs and results.
- **Intent:** the agent drafts it from any briefing dropped in, keeping only what, for whom, what users must do and why. Visual decisions, styles, colors, fonts and named directions are filtered out and listed as **discarded**. The user edits the result.
- **Directions:** the agent proposes about five (family + pieces + why it fits); the user adjusts.
- **Results loop:** screenshots of generated versions are pasted back into the project and pinned. They become references that sharpen the next packs and the taste profile. A result is an ordinary reference that names its project and direction; there is no separate results store.
- The briefing itself is not stored in the library: only the intent drawn from it and the list of what was discarded. Agents never use the discarded list as input for directions, packs or prompts.

**(to specify in M5)**

## 10. Export

An export is a folder `pack-<date>/` with:

- `README.md`: how to use the pack (directions side by side, then the build sequence).
- One subfolder per direction with `prompt.md` (Aesthetic · References · Intent · Guardrails), `image-prompts.md`, and `refs/` (a crop of each piece plus the whole image with the area highlighted).

Where packs are exported is a per-machine setting (§4), not part of the library. By default the export folder contains its own `.gitignore` that ignores everything in it, so a pack placed inside any Git repository is never committed by accident. The user can turn this off per export.

**(to specify in M5)**

## 12. Internationalization

The interface is in English with a Brazilian Portuguese option from the first release. All user-facing strings go through the translation layer from day one. The README has a pt-BR translation in `docs/pt-BR/`.

**Translation layer (`packages/web/src/i18n`).** A small in-house layer, no dependency: one message file per language (`messages.en.ts` is the reference and defines the `MessageKey` type; `messages.pt-BR.ts` is typed `Record<MessageKey, string>`), `translate(language, key, values)` with `{name}` placeholders, and an `I18nProvider` / `useI18n()` pair for React. Components never contain literal user-facing text; they call `t("key")`. The first language is taken from the browser preferences (the first `en` or `pt` tag decides, and `pt-*` gives `pt-BR`; otherwise `en`) and a selector switches it at once. A missing key fails `pnpm check` twice: `tsc` refuses a catalog without every key, and a unit test checks that both catalogs have the same keys, no empty message and the same placeholders. Storing the choice in the per-machine config (§4) arrives with the server.

The interface language is a per-machine setting (§4). The library's `language` (in `library.json`) is something else: the language in which agents write proposals, so the vocabulary stays in one language whichever computer the library is opened on. Validation codes are stable identifiers in English. Messages in `tastelib validate --json` and in MCP results are always in English, so agents and scripts see the same text everywhere; the human-readable output may be translated into the interface language.

## 13. Portability

- Linux, Windows and macOS (Apple Silicon) are all first-class and verified in CI.
- No script that runs on only one operating system. Git hooks are POSIX `sh`, which Git runs on every platform. Workflow helper scripts are plain Node (`.mjs`, no build step, no dependencies), which runs on every platform.
- Text files use LF (`.gitattributes`); the tool reads either line ending.
- Library files are UTF-8 without a BOM, LF, in a canonical JSON form (format-spec §3), so the same data gives the same bytes on every system.
- File names inside a library and a media folder come only from identifiers (ASCII, lowercase, never a Windows reserved name), so they behave the same on case-insensitive file systems and never depend on Unicode normalization. Only the folders the user chooses may have non-ASCII names.
- Paths with non-ASCII characters (for example `Usuário`) are tested in CI. macOS file systems may return such a name in a different Unicode normalization (NFD) than the one passed in, so a path the user gave is stored verbatim, and when a name from a directory listing is matched against a given one, both are compared after `normalize("NFC")`; equality of the raw strings is never assumed.

## 14. Security

See [SECURITY.md](../SECURITY.md) for the sensitive surfaces. The local server listens on the loopback interface only and rejects cross-origin requests.

Library and media paths are built only from identifiers that match the format's patterns, and a media path that resolves outside the media folder (for example through a symbolic link) is refused (format-spec §6.2). JSON files over 8 MiB are not parsed, and nesting deeper than 64 levels is refused before any schema or recursive code sees it (§4 "Reading library files"). Validation reports name files relative to the library and never print absolute paths.

**(to specify in M0 and M2)**

## 15. Testing

- Unit tests next to the behavior; pure logic (schemas, parsers, naming, the intent filter, migrations) always has them.
- End-to-end tests drive the app in a browser.
- Test data is **synthetic and generated at test time**. No third-party images, pages or videos are ever committed.
- CI runs every check on Linux, Windows and macOS, including a non-ASCII path and both line endings in inputs.
- Required checks: `tastelib validate` passes on the sample library; migrations are tested; a made-up briefing full of visual decisions must leak none of them into the intent, and the discarded list must show them all.

### Test layout

- **Unit tests** use Vitest (5.1.0). They sit next to the code as `src/<name>.test.ts`, are excluded from each package's build (`tsconfig.json` excludes them) and are type-checked by a `tsconfig.test.json` in the package (see `packages/testkit`). Every package except `e2e` has a `test` script (`vitest run`, with `--passWithNoTests` while a package has no tests yet); the root `pnpm test` runs them all and is part of `pnpm check` (§3). A package that gets its first test also gets `tsconfig.test.json`, its reference in the root `tsconfig.json`, and a `devDependencies` entry for `@tastelib/testkit` when its tests use it.
- **End-to-end tests** use Playwright (`@playwright/test` 1.64.1) in `packages/e2e`, as `tests/*.e2e.ts`. They are not part of `pnpm check`, because they need a browser download (about 120 MiB). First time: `pnpm test:e2e:install`; then `pnpm test:e2e`, which builds `testkit` first because the tests import its `dist/`. Each test starts its own local HTTP server on an OS-assigned port and serves generated content; nothing touches the network. The package has no `test` script on purpose, so `pnpm test` skips it.
- **Shared helpers** live in `packages/testkit` (`@tastelib/testkit`, private, dev-only). It has no workspace dependencies and nothing ever lists it under `dependencies`. `core` stays free of other workspace packages at runtime; once `core` has tests it lists `testkit` as a `devDependency` only (a test-time edge, not part of the dependency graph in §3). It offers:
  - `makePng(width, height, seed)` and `makeBmp(width, height, seed)`: valid images built byte by byte (no image library), deterministic per seed (same pixels; PNG bytes are stable only within one Node version, because zlib output can change, so tests that need exact bytes use `makeBmp`). JPEG and WebP fixtures arrive with the encoder chosen for compression (M2).
  - `makeHtmlPage({ title, body, images, crlf })`: small HTML pages, with either line ending.
  - `createSeededRandom(seed)`: the PRNG behind the images (mulberry32).
  - `withTempDir(fn)`: a fresh temporary directory whose path contains non-ASCII characters (`.../Usuário-日本`), removed afterwards.
- **Determinism:** fixed seeds, no real network, no dependence on directory listing order or locale; tests that list directories sort the result.
- **No committed binaries:** images are generated at runtime; CI's media check enforces it.

### Format and migration tests

- **Golden libraries.** `packages/core` keeps one hand-written, synthetic fixture library per released format version (JSON only; media is generated at test time), at `packages/core/test/golden/v<N>/`, which is itself a library folder (`library.json`, `references/`, …). A fixture is frozen once its version is released: it is never edited, only added to.
- **Golden media are byte-stable.** The frozen JSON records each media file's `bytes` and `sha256`, so the media a test generates for it must never change. `testkit` gets `makeStablePng(width, height, seed)`: a PNG written byte by byte with uncompressed ("stored") deflate blocks and hand-written CRC-32 and Adler-32, so its output depends on no zlib and no Node version, with a test that pins the SHA-256 of a few outputs. A test helper writes the golden media folder from the golden JSON: the marker with the library's id, and for each media item and frame an image from `makeStablePng` with the listed width and height and, as seed, the 32-bit FNV-1a hash of its media path. The golden libraries therefore list only `image/png` media, with small sizes (at most 64 × 64), and no video until a byte-stable video generator exists; a video reference is then added as a new file (fixtures are only added to). Validating a golden library with its generated media folder and `--checksums` gives no warning, and without a media folder only `media-not-checked`.
- **Schemas** have positive and negative tests for every rule in format-spec, including the canonical serializer (same data, same bytes; `not-canonical` on BOM, CRLF and wrong order) and non-ASCII text in notes.
- **Each migration step N → N+1** is tested for: the golden vN library migrates to a library that validates against the vN+1 schemas; the specific changes the step makes; determinism (two runs give identical bytes); files already at vN+1 pass through unchanged; an interrupted run (stopped after some writes, with the manifest still `in-progress`) is restored from the backup and reaches the same result as an uninterrupted one; the same for an interrupted migration of a library with mixed file versions, where `library.json` is already current; a crash while copying the backup (owner gone, no manifest yet) leaves the originals untouched, and the backup is deleted without restoring; two concurrent recoverers of an `in-progress` backup with a dead owner: only one wins the `owner.json` rename and restores, and the other re-checks and does not restore; a slow recoverer that renames the new `owner.json` of one that already took over finds different bytes, puts the claim back, and does not act; a migration still copying (owner alive, no manifest yet) is not deleted by a second writer, which gets `write-conflict`; a backup folder with no `owner.json` yet, or with an owner on another host, is treated as live; an unreadable manifest is not deleted (the write gets `write-conflict` and the backup is kept); `owner.json` is removed last when a backup is deleted; a backup marked `done` whose owner is gone is deleted without touching the files; and with two concurrent migrations only one claims the backup folder, while the other gets `write-conflict` and does not restore the backup of a live owner.
- **The chain:** the golden v1 library migrates through every step to the current version and validates. A test fails if `CURRENT_FORMAT_VERSION` has no step module, schema folder and golden library for every version up to it.
- **Validate** has one test per issue code (format-spec §16.2), checking severity, file, pointer and exit code, on Linux, Windows and macOS and under a non-ASCII path.
- **Writes** have tests for every allowed agent write and for refusals with `not-allowed` (one per refused kind in format-spec §13.1), for `write-conflict` (the file changes between read and rename), for a multi-file write that stops partway (the primary change is kept, only `dangling-link` warnings remain, and the report lists the files written and not written), for slug derivation (a long name, a name that shortens to a reserved word, a taken slug near 64 characters), for clock skew (a lower bound in the future), and for sequential ids that are never reused after a deletion.

### Core test approach

- **Where test-only code lives.** Unit tests stay next to the code (`src/<name>.test.ts`). Everything else that only tests use sits in `packages/core/test/`, outside `src/`, so the build can never put it in `dist/`: `tsc` refuses an import of it from any build file, because it lies outside `rootDir` (`src/`), and the lint rule of §3 also reports it in pure modules:
  - `test/golden/v<N>/`: the golden libraries (above);
  - `test/support/`: builders of synthetic libraries (`buildLibrary(spec)` writes a small library from typed values through the canonical serializer; `generateLibrary({ references, seed })` writes the large one of the performance budget), fault-injecting file systems and pause points;
  - `test/migrations/` and `test/schemas/v2/`: the test-only step and schemas (below);
  - `test/processes/`: plain `.mjs` drivers that child-process tests start.

  `packages/core/tsconfig.test.json` sets `rootDir` to the package folder and includes `src/**/*.test.ts` and `test/**/*.ts`, so all of it is type-checked. Helpers that do not depend on `core` (byte-stable images, temporary folders) stay in `testkit`; the builders depend on `core`'s types, and `testkit` can never depend on `core` (§3), so they stay in `core`. Tests of other packages that need the golden library find it by path from the repository root; it is data, not a package import.
- **Biome never formats the golden libraries.** Its JSON formatter rewrites canonical JSON (for example it puts `["calm", "dense"]` on one line), so `biome.json` excludes `packages/core/test/golden/**`; otherwise `pnpm format` would edit frozen fixtures. `.gitattributes` already keeps them LF on every checkout.
- **The migration runner at version 1.** The runner and the reader take the format registry (`format.ts`) as a parameter; production passes the real one (`CURRENT_FORMAT_VERSION` 1, no steps). Tests pass a test registry with version 2: test-only v2 schemas in `test/schemas/v2/`, built from the v1 modules with zod's `extend` and the changes below, a v2 folder layout, and a test-only step in `test/migrations/v1-to-v2.ts` that is pure and deterministic like a real one and does each thing a real step may do: it sets `formatVersion` 2 in every file (changes), splits `glossary.json` into one file per term at `glossary/<term-id>.json` (adds files and removes one, so the manifest's added files and the deletions run), and copies `library.json`'s `language` into each `project.json` (moves data between files). Every runner test of §15 above runs with it: the golden v1 library migrates and validates against the test v2 schemas, determinism, pass-through of files already at v2, mixed versions, interruption and recovery.
- **Runner failures.** With injected I/O errors after the claim, after the manifest, after some step-5 writes and after `done`, a migration cleans up its own backup: the library is byte-for-byte as before (or migrated, after `done`), no backup is left, the result is `failed`, its `notices` hold `migrated` only in the case after `done`, and the next write in the same process succeeds. After some step-5 writes, only the files already replaced or deleted are restored and only the added files it created are removed; a file it had not reached is never touched. A file changed outside `tastelib` before its step-5 write gives `refused` with `write-conflict`, the files written before it are restored, and the changed file keeps its new bytes. A file changed between step 1 and the re-read after the claim (changed once before the `mkdir` claim, and once from the `claimed` hook) gives, in both cases, `refused` with `write-conflict` before the manifest: the backup is deleted (`owner.json` last), no copy holds the old bytes, and every library file is untouched. When the cleanup fails too (an injected error during a restore), the backup stays, a second runner (another injected `pid`, probe `alive`) gets `write-conflict`, and the next write in the owning process finishes the cleanup first, accepting files already restored or removed by the interrupted cleanup (a cleanup interrupted after removing an added file and before restoring a deleted one is finished by the resumed cleanup: the added file stays absent and the deleted file comes back with its backed-up content), but not if `owner.json` no longer holds its bytes, and not past a file in any other state (`write-conflict`, backup kept). A crash (`SimulatedCrash`) at the same points cleans up nothing.
- **The chain test at version 1** checks that the production registry's versions are exactly 1 to `CURRENT_FORMAT_VERSION`, with a step for each version below the current one and no other; that for every version there are `src/schemas/v<N>/set.ts` and `test/golden/v<N>/library.json`, and for every version above 1 `src/migrations/v<N-1>-to-v<N>.ts`; and that every golden library migrates through the production chain to the current version and validates with no error and no warning (at version 1: no step, and the golden v1 library validates). The same chain logic also runs once with the test registry, so it is exercised with a real step before the first real one exists.
- **The media marker** has its own registry (version 1, no steps), separate from the library's (format-spec §15.1), passed the same way. Its tests inject a test-only marker step v1 → v2 (it sets `formatVersion` 2 and adds one field) with a test-only v2 marker schema, also under `test/`, and check: an older marker is migrated on disk when the folder is attached or written to, and in memory only by read-only commands; a newer marker blocks media writes while the library stays writable; and the marker never counts for `mixed-format-versions`.
- **Crash points.** The file-system modules use a small file-system adapter (the subset of `node:fs/promises` they need) and accept hooks: `fs` (default the real one), `probe` (`(pid) => "alive" | "gone"`), `hostName` and `pid` (default `os.hostname()` and `process.pid`), `platform` (for the Windows retry path) and `at(point)`, called at every named step of the runner and of recovery (`claimed`, `owner-written`, `copied:<path>`, `manifest-written`, `wrote:<path>`, `library-json-written`, `done-written`, `deleted:<path>`, `owner-deleted`, `taken`, `own-owner-written`, …). A test simulates a crash by throwing `SimulatedCrash` from `at`: it carries no `errno` code, so no result path catches it and nothing is cleaned up (§4 "Cleanup only on result paths"), as when a process dies. The "dead" owner is then reported `gone` by the test's probe, and a second runner (another injected `pid`) recovers. A wrapping file system injects I/O errors (`EPERM` on a rename a given number of times, `EIO`, `ENOSPC`) the same way.
- **Concurrency.** The orderings of the takeover protocol (two recoverers, a slow recoverer that takes the new claim of a winner, a writer meeting a migration still copying) are tested deterministically in one process: `at` returns a promise, so a test pauses one runner at a named point, runs the other to a point or to the end, then resumes the first. Real child processes (`process.execPath` with a driver in `test/processes/`, which imports the built `dist/`) cover what only the operating system can show: eight processes racing for the non-recursive `mkdir` claim (exactly one wins, the others get `write-conflict`), and a process killed after its claim, whose process id the real probe then reports `gone` on Linux, Windows and macOS. `core`'s `test` script becomes `tsc -b && vitest run`, so `dist/` is current when the drivers run.
- **The process probe** calls `process.kill(pid, 0)`: `ESRCH` means gone; success or any other error (`EPERM`: alive but not ours) means alive, so in doubt the backup is treated as live, never deleted. Node documents signal 0 as "a platform independent way to test for the existence of a process"; on Windows, libuv opens the process and checks that it has not exited. A `pid` in `owner.json` that is not an integer from 1 to 2^31 − 1 makes the file unreadable (case 1 of format-spec §15.3): `process.kill(0, 0)` and `process.kill(-1, 0)` signal a process group or every process and always succeed (on Windows, pid 0 means the current process), and Node refuses pids above 2^31 − 1.
- **The performance budget** (§4 "Index") is an ordinary test in `pnpm test`: it generates the library in a temporary folder (not timed), opens it once untimed to warm up, then times each budget line once. It sets its own Vitest timeout, since generating 17 MB of small files is slow on Windows.

The check command is in §3.
