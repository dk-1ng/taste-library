# Design

This document is the source of truth for what taste-library does. Behavior is defined here before it is built, and a change to what users or agents see updates this document in the same pull request. The on-disk data format is specified separately in [format-spec.md](format-spec.md), the public contract that the tool, agents and integrations follow.

**Scope.** This document records what is visible from outside (the commands, their options, codes and outputs, the files the tool writes, and the public API of `core`) and the promises the tool keeps, in one or two sentences each. How the code keeps a promise (steps, order, timings, formulas, retries, internal checks) is not recorded here: the code and its tests are the record, with a doc comment where a reason would otherwise be lost. Plans live in the issues; the decision log (§18) holds one row per live decision, and the evidence lives in the issue or pull request it names.

**Reviews grade by promises** (§14 "Threat model"). A blocker is code that breaks a promise or a contract of this document or of format-spec, or a hard rule, under a condition in scope of §14; or a change to what users or agents see that the docs do not record. Code that differs from a description of mechanism is not a blocker: the fix is to remove the description.

Agents and people read this document by section, the headings first (`grep -n '^#' docs/design.md`), then the sections they need (`CLAUDE.md`, "Reading the docs").

Sections marked **(to specify in Mx)** are placeholders that the named milestone fills in.

## 1. Purpose and audience

taste-library helps people inject their own design taste into AI-assisted design and avoid generic, regressed-to-the-mean interfaces. It serves a method in three steps: build a taste library of high-quality references grouped into aesthetic families; use a few focused tools; and build in sequence, never in one shot, with prompts made of four elements (**Aesthetic, Reference, Intent, Guardrails**), several directions side by side, then refinement.

Audience: people who already use AI coding agents (Claude Code, Cursor, Codex and similar). No design or development background is assumed for using the app itself.

## 2. Principles

1. **Local-first and private.** Runs on the user's machine, works offline, needs no account, sends no telemetry.
2. **Plain files are the truth.** The library is a folder of small, readable files. Any index is disposable and rebuilt from the files.
3. **The user's words are sacred.** Notes are stored verbatim. Interpretation is a separate layer, marked `to-review` until accepted or corrected.
4. **Intent only from briefings.** A project takes from a briefing only what it is, for whom, what users must do and why. Visual decisions are filtered out and listed as discarded.
5. **Agents work on the same files**, but write only through `tastelib` (CLI or MCP), which validates every write.
6. **The tool produces inputs and takes outputs back.** It does not integrate specific design or image services; it exports what they consume and imports what they produce.

## 3. Architecture

A TypeScript monorepo (pnpm workspaces):

```
packages/
  core/     data format: schemas, validated read/write, index, migrations
  server/   local server: API, URL capture, compression, video
  web/      user interface (React), translations en / pt-BR
  cli/      the `tastelib` command (init, validate, doctor, migrate, config; later open, process, export, ...)
  mcp/      MCP connector for any agent
  testkit/  dev-only test helpers: generated fixtures, non-ASCII temp directories
  e2e/      end-to-end tests (Playwright)
agent-kit/
  claude-code/   Claude Code plugin (commands and skills)
  AGENTS.md      the same instructions for other agents
docs/
examples/sample-library/   only the maintainer's own or freely licensed media
```

Planned building blocks (each confirmed or replaced when its milestone starts): React + Vite for the interface; Hono for the local server; zod for validation; a headless Chromium or Firefox for URL capture, driven by an engine that #45 chooses (§5 "URL capture"); image and video encoding chosen by #44; Vitest and Playwright for tests; GitHub Actions on Linux, Windows and macOS; a pinned Node LTS.

`sharp` and `ffmpeg-static`, planned at first for media, are ruled out by rule 7 with no exception: `sharp` itself is Apache-2.0, but the libvips binaries it installs (`@img/sharp-libvips-*`) are LGPL-3.0-or-later, and `ffmpeg-static` is GPL-3.0-or-later. Both would ship with the server at run time, so neither is a development-only dependency. #44 chooses what replaces them, under the same rule.

### Compiler configuration

- `tsconfig.base.json` holds the shared options (`target` and `lib` `es2025`, `module` `nodenext`, `strict` with `noUncheckedIndexedAccess`, and the rest listed in that file). Paths use `${configDir}`, so every package compiles `src/` to `dist/` (`e2e` is the exception: it compiles `tests/` and its Playwright config, declarations only) and keeps its `.tsbuildinfo` inside `dist/` (deleting `dist/` forces a rebuild).
- Each package's `tsconfig.json` extends the base and adds only `types` and `references`, plus an `exclude` for `*.test.ts` when it has unit tests (type-checked by its `tsconfig.test.json`, §15). Node packages set `types: ["node"]` and write relative imports with the `.js` extension. `web` sets `module` `esnext`, `moduleResolution` `bundler`, `jsx` `react-jsx`, `lib` `["es2025", "dom"]`, emits declarations only (Vite produces the bundle) and writes relative imports without an extension.
- The root `tsconfig.json` is a solution file (`files: []`, references to every package and to the test configs) for editors and `tsc -b` from the root.
- The configuration avoids every option that TypeScript 6.0 deprecates, so moving to TypeScript 7 is a version bump (§18, the TypeScript row).

### Build

- Each package's `build` script is `tsc -b`. `pnpm -r build` runs them in dependency order; `pnpm build` at the root does the same, and `pnpm clean` runs `tsc -b --clean`.
- `web`'s build is `tsc -b && vite build`: `tsc` type-checks and emits declarations, Vite writes the app to `packages/web/dist/app`. `pnpm --filter @tastelib/web dev` starts the Vite dev server.
- Scripts in any `package.json` call only cross-platform programs (`tsc`, `pnpm`, `vitest`, `playwright`, later `vite`). No shell built-ins (`rm`, `cp`, `mkdir -p`), no inline environment variables (`FOO=1 cmd`), no quoting or globbing that only a POSIX shell understands. A step that needs more is a Node script.

### Check command, lint and format

- `pnpm check` is the single gate, run locally, by agents (loop step 5) and in CI: `pnpm lint && pnpm format:check && pnpm typecheck && pnpm test && pnpm build`. It stops at the first failure and exits non-zero.
- Biome does both linting (`recommended` rules; `pnpm lint` fails on warnings too) and formatting (2 spaces, double quotes, semicolons, 100 columns, LF). `pnpm format` rewrites files; `pnpm lint` and `pnpm format:check` only report.
- Biome is limited to code and data files (`.ts`, `.tsx`, `.js`, `.mjs`, `.json`), listed in `biome.json`. Markdown and YAML are not touched: it would reflow tables and prose in the design documents. It honors `.gitignore`.
- `pnpm typecheck` is `tsc -b`. `pnpm test` runs each package's `test` script when it has one (`pnpm -r --if-present test`); the test layout is in §15.
- `pnpm install` runs `prepare`, which runs `scripts/setup-hooks.mjs`: it sets `core.hooksPath` to `.githooks` in a Git checkout and does nothing elsewhere. New clones get the hooks without a manual step.
- CI runs `pnpm check`, then the end-to-end tests (`pnpm test:e2e:install`, `pnpm test:e2e`), on Linux, Windows and macOS (`ubuntu-latest`, `windows-latest` and the runner named by the repository variable `MACOS_RUNNER`, default `macos-latest`; the jobs are named `Check (linux|windows|macos)` and `Workflow tooling (linux|windows|macos)`, and the ruleset on `main` requires those names) with the Node version from `.nvmrc` and the pnpm version from `packageManager`. The pnpm store is cached through `pnpm/action-setup` (`cache: true`); actions are pinned to full commit SHAs and `zizmor` audits the workflows.
- Dependabot watches the npm ecosystem weekly with a 7-day cooldown, groups development dependencies into one PR and uses the `chore(deps)` prefix.

### Core modules and API

`core` has two entries. `@tastelib/core` is the Node entry and exports everything. `@tastelib/core/browser` (`exports["./browser"]`) exports pure modules only, which run unchanged in Node and in a browser, so `web` can use them from M2. Everything that touches the operating system lives in `packages/core/src/node/`. The folder layout and what each module holds are documented in `packages/core/src/index.ts`.

- **Pure** means: imports only `zod` and other pure modules through relative paths, never an entry (the two entries are the only barrel files in `src/`), and uses no Node-only global (`process`, `Buffer`, `setImmediate`, `clearImmediate`, `require`, `module`, `__dirname`, `__filename`) and no global object (`globalThis`, `global`, `self`, `window`), so every global is named directly where the rule can see it. Globals that Node and browsers share (`TextDecoder`, `TextEncoder`, `crypto.getRandomValues`, `URL`, `structuredClone`) are allowed and used by their bare names. SHA-256 (for `inputSha256` and `proposal-stale`) is passed in by the caller as a synchronous function (`node:crypto` in `node/`), because the browser's Web Crypto `digest` is asynchronous.
- **Checked by a lint rule**, so `pnpm lint` fails at the offending line: an `overrides` entry in the root `biome.json` covers `packages/core/src/**` except `node/**`, `index.ts` and `*.test.ts`. Pure is the default: a new folder is pure unless it is under `node/`. It is a lint rule, not a sandbox: code written to get around it, such as `Function("return this")()`, is not reported, so code review still watches pure modules for it.
- **Test-only code is never under `src/`** (§15 "Core test approach"), and the build's `rootDir` is `src/`, so nothing test-only can reach `dist/`.

**Public API for M2 and M3** (names are indicative; the shapes are the decision):

- `openLibrary(root, options)` reads every library file once and returns either `{ ok: true, library }` or `{ ok: false, code, message }` with `code` `not-a-library` (no `library.json`) or `unreadable-folder`; the CLI turns those into exit 2 (format-spec §16.1). `library` is a handle that long-running processes (the M2 server, the M3 MCP connector) keep open.
- `library.snapshot()` returns an immutable **snapshot**, refreshed first (§4 "Index"): `formatVersion` (of `library.json`, or `null`), `files` (a map sorted by relative path; for each file its kind, its exact bytes, its fingerprint (`null` for a snapshot built in memory), its `formatVersion`, its status `valid`, `invalid`, `newer` or `unreadable`, its parsed value when valid, at the file's own version, and its own issues, checked against the schemas of its own version), `migrated` (below), `issues` (the whole report, sorted as in format-spec §16.3) and `index`. **The migrated view:** when the library is older or mixed (format-spec §15.2) and the migration can run (no file with errors at format-spec §15.3 step 1 and no error left at step 3), `migrated` is a snapshot of the library as the migration would leave it, built in memory by the same steps 1–3 that the migration runner and `tastelib migrate --dry-run` use, so the three never disagree: its files are at their migrated paths, with their values at the current version and every fingerprint `null`. Otherwise (a current library, or a migration that cannot run) `migrated` is `null`. A step works on the whole library and may add, move or remove files (format-spec §15.4), so `migrated` is library-wide, never a value per file on disk. A refresh reuses every unchanged file's entry, so snapshots share structure and cost little to keep.
- **The report** is `reportOf(registry, snapshot, mediaIssues?)` (pure): the snapshot's issues plus the media issues the caller passes, sorted and counted in the shape of format-spec §16.3. Without `mediaIssues` (no media folder on this computer) it adds `media-not-checked` once. Every `snapshot()` refreshes first, the first one after `openLibrary` included, reusing each unchanged file's entry by its fingerprint, and when nothing changed it returns the previous snapshot object itself (§4 "Index"). A file whose version is below the current one is checked against the schemas of its own version, which gives its own issues. When `migrated` exists, the cross-file checks run on it instead of on the files on disk, and the report holds the issues of each file on disk and of the listing, `needs-migration` and `mixed-format-versions`, and the cross-file issues of `migrated`, each at its migrated path and pointer, with a message that says it was found after migration to version N (the path may not exist on disk yet, for example a file the migration adds). When `migrated` is `null` because the migration cannot run, a file below the current version takes no part in the links of the cross-file checks (a link into or out of it is unresolved), and the errors left at step 3 are still in the report, at their migrated paths, so the report has an error exactly when the write gate would refuse to migrate; errors at step 1 are already the issues of files on disk. `needs-migration` (library.json below the current version) and `mixed-format-versions` come from the files on disk and do not depend on `migrated`. In the cross-file checks a link into a file that is absent is `dangling-link`, and a link into a file that is not `valid` is unresolved (below, "Links to files with errors"); `name-mismatch` is reported at `/id` (references) or `/slug` (families, and projects against their folder) unless that value already breaks its own rule. A format folder that exists but cannot be listed is reported as `unreadable-file` and everything under it is unresolved, never dangling; a folder that disappears between two listings is treated as deleted; a symbolic link that cannot be followed, or that leads outside the library (§4 "Reading library files", "Links stay inside the library"), where a file or a format folder belongs is `unreadable-file` (a folder this way is also unlisted, so what is under it is unresolved), and with a name the format does not know it is `unexpected-file`.
- `checkMedia(snapshot, mediaRoot, { checksums })` returns the media issues separately, so refreshing a snapshot never hashes media.
- `attachMediaFolder(library, path)` attaches a media folder (§4 "Attaching a media folder"): it returns `attached` (with `marker` `written`, `kept` or `migrated`), `refused` (a stable code, message and issues) or `failed` (`io-error`), and never throws for them. `guardMediaWrite(mediaFolder, libraryId)` is what every media write (a capture, a deletion) calls first: it refuses without a valid marker of this library, refuses a newer one (`newer-format`, the library stays writable) and migrates an older one on disk; `readMarker` is the same read with the migration in memory only, for read-only commands. The marker has its own registry and steps (`MARKER_REGISTRY`, format-spec §15.1). `findGitWorkTree(path)` and `isInside(inner, outer)` are the Git walk and the folder-identity comparison of §4 "Comparing folders".
- `library.write(build, options)` runs the write pipeline (§4 "Writing library files"). `build` receives the fresh, gated snapshot and returns a **plan**: `{ changes, skipped, blockedBy? }` (plain data). `changes` is an ordered list of file changes (`{ path, next }`, `next` being the new value or `null` for a deletion), the first one being the primary change (format-spec §5), written in that order; `skipped` lists the files, or the folders that could not be listed, that the operation chose to leave alone, each `{ path, reason }` (for example link removal skipping a file with errors, §4 "Links to files with errors"), and is passed through unchanged to the result; `blockedBy` lists files the plan depends on without changing them (for example the file that holds an entry to delete), and the write is refused with their issues when one is not `valid` (§4 "Writing library files", layer 2). A plan that breaks its own shape (a path twice, a path of no file type, a deletion of `library.json` or of a file the snapshot does not hold, `blockedBy` naming a file the snapshot does not hold outside a folder that could not be listed) is a bug and throws. The deletion planners (a pin, a reference, a family, a guardrail, a direction; pure, exported by both entries) build their plans from the snapshot, link removal included (§4, "Deleting"). Because the plan is built after the gate, a write that first migrates the library builds its plan on the migrated files. Writes through one handle run one at a time, in order, so two requests in one process never race each other; across processes the optimistic check decides.
- `library.migrate(options)` runs the write gate with no plan (§4 "`tastelib migrate`"), in turn with the handle's writes, and returns `current` (nothing written, not even `.tastelib/`), `migrated` (with `from`, `to` and the files `changed`, `added` and `removed`, sorted by path), `refused` (`issues`) or `failed` (a `failure`), each with `notices` as in a write result.
- **Issues** are plain data in the exact shape of format-spec §16.3: `{ severity, code, file, pointer, message }`, with `file` relative to the library with `/` (or `media:…`, or `null`), never absolute. The severity of a code is always the one in format-spec §16.2, also in a refusal.
- **Errors that are not validation issues** never become an `Issue`, because format-spec §16.2 is the contract of the validation report and gains no code without a new format version. They are returned as results with their own stable codes: `not-a-library` and `unreadable-folder` (open) and `io-error` (a file could not be read back, written, flushed, renamed or removed during a write: `{ code: "io-error", operation, file, errno, message }`, with `file` relative to the library). The command line adds them to its list of codes. A read failure while opening is the issue `unreadable-file`, as format-spec §16.2 says. Expected failures are never thrown; a thrown exception means a bug.
- **A write result** has a `status` and, whatever the status, `notices` (empty when there are none), for example `{ code: "migrated", from, to }`: `migrated` is in `notices` exactly when the gate's migration reached the manifest marked `done` (format-spec §15.3 step 6), whatever the final status, including refused, unchanged or failed, because the library was then migrated on disk; a migration that was undone by the runner's own cleanup, or that never wrote, gives no `migrated` notice. The statuses are `written` (with the files written and `skipped`, taken from the plan's `skipped`), `unchanged` (the plan changes no file, so nothing is written and no `updatedAt` moves), `refused` (a check stopped it: `issues`, for example validation errors, a new `dangling-link`, `write-conflict`, `newer-format`, a migration that cannot run, later `not-allowed`) or `failed` (a `failure` with its code: `io-error`, or `not-a-library` or `unreadable-folder` when the folder stopped being a readable library after it was opened). `refused` and `failed` also list the files written and not written, which are both non-empty only when a multi-file write stopped after its first rename (format-spec §5). For a write of one file, `written` is empty and `notWritten` is empty when the write was refused before it reached the disk (validation, a new `dangling-link`, the gate) and holds the file when the write stopped at the replace or after it (`write-conflict` at the rename, `io-error`), except that the file is in `written` when only the folder flush failed (`applied`).


## 4. Library, media and configuration

- A **library** is a folder (usually its own private Git repository) holding the data files described in [format-spec.md](format-spec.md).
- **Media** (images, full-page captures, videos, frames) lives in a separate **media folder**, outside any Git repository. It can be any folder, including one kept in sync by a file-sync service; the tool never depends on a particular service.
- The tool refuses a media folder that sits inside a Git working tree, inside the library folder or that contains the library folder, and a folder that is not empty and has no marker, with no exception (§4 "Command line", "Attaching a media folder"); `tastelib doctor` checks it.
- Media that a library references but that has not arrived yet (for example, still syncing from another computer) is shown as **awaiting sync**, never as an error.
- **Per-machine configuration** (where the library and the media folder are on this computer) lives outside the library: `~/.config/tastelib/config.json` on Linux and macOS, `%APPDATA%\tastelib\config.json` on Windows. It is never committed. It also holds the other settings that belong to one computer: the interface language (§12) and where packs are exported (§10). The library itself holds no machine path.
- **The config file** is JSON with `version` (`1`) and these optional fields: `libraryPath`, `mediaPath`, `packsExportPath` (absolute paths in the form of the operating system that reads the file, with no `.` or `..` segments), and `language` (`en` or `pt-BR`). Unknown fields are refused. A missing file means the defaults (`{ "version": 1 }`). On Linux and macOS, `$XDG_CONFIG_HOME` is used when it is an absolute path, otherwise `~/.config`. A file over 1 MiB, or one that is not a regular file, is not read (a symbolic link to a regular file is followed, and the size is checked on the file it points to). Every error, including a failed write, is a `ConfigError` that names the config file and, when it concerns one, the field. It is written atomically (temporary file in the same folder, `fsync`, rename), and a write that fails validation leaves the old file untouched. A `mediaPath` inside a Git working tree (a `.git` folder or file in the path or any parent, after resolving symbolic links) is refused when the config is written.
- A media folder belongs to one library: it holds a marker file with the library's id (`tastelib-media.json`), so attaching the wrong folder is detected.
- Every write goes through `tastelib`, is validated first and replaces the file atomically (temporary file in the same folder, then rename). The exact rules, including how `tastelib validate` reports errors and warnings, are in [format-spec.md](format-spec.md) §16.
- **Concurrent writers** (the app and an agent at the same time) are handled by an optimistic check: just before the rename, the writer reads the file again and compares it with the bytes it started from; if they differ it refuses with `write-conflict`, and the caller reads again and retries (format-spec §5). There is no lock file. If real use shows conflicts the check cannot catch, M1 or later adds a lock. A write that touches several files (a deletion that removes links, a merge) is not atomic as a whole: `tastelib` checks every file before the first rename, writes the user's decision first and removes links after, and reports which files were written if it stops partway, so a partial stop leaves at worst dangling links, never a lost decision (format-spec §5).
- **Timestamps** are UTC. Because clocks on two computers may disagree, a writer sets `updatedAt` and `reviewedAt` to the later of now and their lower bound (format-spec §4.1), so a skewed clock never makes a write fail.
- **Format versions.** Read-only commands migrate an older library in memory only. Before its first write to an older library, or to a library whose files have mixed versions, `tastelib` migrates it on disk automatically and says so; `tastelib migrate` (with `--dry-run`) does it on request. A migration is validated completely before anything is written, keeps a backup until it finishes, and writes `library.json` last. The migrating process claims the backup folder with a non-recursive `mkdir` (only one can succeed), writes `owner.json` with its process id and host name before copying anything, copies the files into it atomically, and only then writes a manifest marked `in-progress`; the manifest is marked `done` after `library.json` is written, and only then is the backup deleted, `owner.json` last. The copies, `owner.json`, both manifest writes, every library file the migration writes and every file a recovery restores are flushed to disk (`fsync` of the file before its rename, and of each touched folder after it where the operating system allows it) before the next step, so a power cut can neither leave a backup that recovery would trust but that is empty, nor a manifest marked `done` over library files that never reached the disk. No other write runs while a backup exists: with no owner file yet, an owner on another host, a live owner, or an unreadable manifest, the write fails with `write-conflict` (retry later) and the backup is kept; with the owner gone, a backup marked `done` or with no manifest (the copy never finished; the originals are untouched) is deleted, and one `in-progress` is restored and the migration runs again (format-spec §15.3). Several processes that find the same abandoned backup race for it by renaming `owner.json` to a unique name. A rename that succeeds wins only if the renamed file holds exactly the bytes of the `owner.json` the recoverer judged gone; otherwise it has taken the live claim of a recoverer that already won, puts it back with an exclusive create (`wx`) and checks again. The winner creates its own `owner.json` exclusively too, so it can never replace someone else's, deletes the renamed file, and recovers; the others check again from the start. A restore during recovery overwrites files that changed after the interruption (for example through a `git pull`); their newer versions remain in Git history. When a backup stays stuck (a reused process id, a crash right after the claim, just before the folder is removed, or by a takeover winner before it created its new `owner.json`, an unreadable manifest, or a computer that was renamed and now looks like another host), `tastelib doctor` reports it, and `tastelib doctor --resolve-migration` shows what it holds and, after the user confirms, restores or deletes it. Before a restore it warns that restoring overwrites any of those files that changed since the interruption, for example through a `git pull`. Unlike the rest of `.tastelib/`, the backup folder must never be deleted by hand or by cleaning tools such as `git clean -X` while a migration is in progress or interrupted (format-spec §5). The version in `library.json` does not decide this, because a library with mixed file versions migrates while `library.json` is already current. There are no down-migrations; Git history is the way back. The media folder's marker has its own version: it is migrated on disk when the media folder is next attached or written to, and in memory only by read-only commands.
- **Deleting** a pin, a reference, a family, a guardrail or a direction is a multi-file write planned by `core`'s deletion planners: the primary change first (the pin removed from its reference with its interpretation, keeping `lastIssued`; the reference or family file deleted; the guardrail or direction entry removed, keeping its file even when it becomes empty and keeping `lastIssued`), then one change per file that holds a link to it, sorted by path: a pin or a reference from families, the glossary, guardrails, the taste profile and directions (`PieceRef`); a family from directions (`family` becomes `null`); a guardrail from directions; a direction from references (`result.direction` becomes `null`). Removing a link moves the `updatedAt` of the file or entry that held it (layer 6) and edits no `Authored` value (format-spec §4.6). Running a deletion again after it stopped partway completes it: when the thing is already gone, the plan removes only the links left over, and with none left it changes nothing (`unchanged`).
- **Deleting a reference** follows the multi-file write order of format-spec §5: the optimistic check on every file it will touch first (any change refuses the whole deletion), then the reference file itself (the primary change, the user's decision), then the links to its pieces in other files (families, glossary, guardrails, taste profile, directions, format-spec §14), then its folder in the media folder, through the media write guard (format-spec §6.1). A stop after the reference file is gone leaves at worst `dangling-link` and `orphan-media` warnings, never an error and never a lost decision. Removing links first would be wrong: a stop partway would drop the user's accepted family memberships while the reference survives. When the media folder is not attached on this computer, or the reference's folder is not there (still syncing), the deletion still completes; a folder that turns up later is reported as `orphan-media`.

How `core` builds this is below; its modules and API are in §3 "Core modules and API". The commands that create a library, set and attach the folders on this computer, check the setup and migrate are in "Command line" at the end of this section.

**Writer rules at a glance.** Every writer in `core` follows these, each defined once in the section named:

- **Region rounding:** each axis in integer millionths, the size kept at least 1e-6, the position at most 1 − 1e-6, and the size clamped to `1 − position` when the sum passes 1 (for example `w = 1 − x`), so `x + w ≤ 1` always holds; applied only to values that already passed validation (§4 "Writing library files", "Proportions").
- **Windows `rename` and `unlink` retries:** on `EPERM`, `EACCES` or `EBUSY`, retried until 2 seconds have passed since the first failure, waiting 10 ms first and doubling up to 250 ms, with the optimistic check repeated before each retry; on Linux and macOS never retried (§4 "Writing library files", "Windows renames and deletions").
- **A write that fails for an I/O reason** ends `failed` with `{ code: "io-error", operation, file, errno, message }`, `file` relative to the library. It is a result code of `core` and the command line, not a format-spec §16.2 code, so the format is unchanged (§3 "Core modules and API").
- **Deeply nested JSON:** more than 64 levels of objects and arrays is `invalid-json` ("nested deeper than 64 levels"), never thrown (§4 "Reading library files").
- **Every write** `fsync`s its temporary file before the rename; folders are flushed only in durable mode, never on Windows (§4 "Writing library files", "Durability").

### Reading library files

- **Rules across fields run on the raw input.** zod would skip an object's refinement when a field inside it has the wrong type, hiding duplicate ids, local links, kind against type, `updatedAt` against `createdAt` and `lastIssued` until the types are fixed. The schemas therefore register those rules as checks that always run, which read the input without trusting its shape and report a rule only when the values it is about are well-formed, so a malformed value is reported once, by its own rule (format-spec §16.2, "one issue per rule broken"). One exception, kept on purpose: a list over its maximum (for example 51 tags or 501 pins) stops the rules of the objects above it, because zod does not parse a list that long; that bound protects the reader from huge input, and the list's own issue is reported.
- **Links stay inside the library.** Until this is built (#92), the reader follows every link and a write through a link can land outside the library; the rest of this bullet and §14 state the behavior once it is built. Every file the tool reads or writes in a library, and every folder it lists or creates there, is the library's real folder or lies under it once symbolic links and junctions are resolved, so a library cloned from someone else cannot lead a read or a write to another place (§14 "Threat model"). The library folder itself may be a link or a junction (for example a library kept on another drive): it is resolved with `realpath` on each listing and each write, and the real folder it gives is "the library". Inside it, every format folder the listing walks (`references/`, `families/`, `projects/`, each `projects/<slug>/`) and every entry the listing sees as a symbolic link or a junction is resolved the same way and compared with the library's real folder by identity, as in §4 "Attaching a media folder", "Comparing folders"; an entry that is not a link, in a folder that is inside, is inside, so a library without links costs no extra call per file.
  - A file that leads outside is `unreadable-file` ("a symbolic link or junction that leads outside the library") and is never opened, so none of its content reaches a report, the app or an agent. A format folder that leads outside is a folder that cannot be listed: `unreadable-file` on the folder, and everything under it unresolved (§4 "Links to files with errors"). The message never says where the link leads (reports hold no absolute paths, format-spec §16.3). `library.json` follows the same rule, also when a command looks for its library: one that leads outside its folder is a file that cannot be read (§4 "Which library a command uses"), and the library's version is then unknown, so writes are refused (§4 "Write gate").
  - `.tastelib/` follows it too. `validate` still ignores that folder (format-spec §5), but when it leads outside, every write is refused before the gate looks for a migration backup, with `unreadable-file` at `.tastelib` ("the tool's working folder is a symbolic link or junction that leads outside the library; remove the link"), because the tool would otherwise trust, or create, a migration backup in another folder.
  - A link that stays inside the library is refused too when it resolves to `.tastelib/` or `.git/` or under either of them (compared by identity, as in §4 "Attaching a media folder", "Comparing folders"): those folders are not part of the format, Git does not carry what is behind a link into them, and the tool or the user may delete them at any time (format-spec §5), so notes written there would be lost without a sign. A format folder or file that resolves there is treated as one that leads outside, with the same `unreadable-file` and a message that asks to remove the link.
  - Other links that stay inside are followed as before (a reference that links to another file of the library is read, and then reports its own `name-mismatch`). A link at a file path is never followed by a write: the rename replaces the link and a deletion removes it (§4 "Writing library files", "Links on the way to a file"). Links to special files stay `unreadable-file` (below). Hard links are files like any other; Git and sync services do not carry them.
  - **Setups that are not supported:** a format folder or file of the library moved elsewhere through a link or a junction (for example `references/` on another drive): it is reported as above and not read. To keep a library elsewhere, move the whole library folder, or make the library folder itself the link; the media folder has its own rule (format-spec §6.2). In a Git library that setup never worked: Git commits the link, not the files behind it (§18, the row on links inside the library).
- **I/O.** A file is read through one handle (size check and read on the same handle): over 8 MiB gives `file-too-large` and is not parsed; a read error gives `unreadable-file`, and so does a path that is not a regular file once opened (it is opened without blocking, so a link to a FIFO or to `/dev/zero` never hangs the reader); a file that disappears between the listing and the read is treated as deleted. Opening a library keeps up to 16 reads in flight, and results are ordered by path, never by completion. The exact bytes are kept in the snapshot for the optimistic write check (format-spec §5).
- **The strict reader** is a pure function from bytes to a value or issues, and is original code: an RFC 8259 parser with an explicit stack, never recursion.
  - Decoding uses `TextDecoder("utf-8", { fatal: true, ignoreBOM: true })`; a decoding failure gives `invalid-encoding` (pointer `null`). A leading U+FEFF is skipped and recorded, and so are CR characters, so a `not-canonical` message can say why.
  - Duplicate keys are found while parsing, comparing the decoded keys (so `"a"` and `"\u0061"` are the same key), and give `duplicate-key` at the pointer of the repeated key (`/pins/0/note`). A string or key that decodes to a lone surrogate (`!isWellFormed()`) gives `invalid-encoding` at its pointer. The reader goes on after these two, so every one is reported, and stops at the first syntax error, which gives `invalid-json` (pointer `null`, with line and column in the message).
  - Numbers are checked against the RFC 8259 grammar and converted with `Number()`, the same correctly rounded conversion as `JSON.parse`. Range rules (integers up to 2^53 − 1, finite proportions) belong to the schemas.
  - A key named `__proto__` becomes an own property, as with `JSON.parse`, so the strict schemas report it as an unknown field and no prototype is touched.
  - **Nesting is limited to 64 levels** of objects and arrays; deeper input gives `invalid-json` ("nested deeper than 64 levels") and is never thrown. RFC 8259 §9 allows a parser to limit nesting depth, so this is still plain JSON and needs no new code. The deepest v1 file has 5 levels (a reference's `interpretations` → piece → `proposal` → `vocabulary`). The limit is needed whichever parser is used, because zod and every recursive walk overflow far below the depth `JSON.parse` accepts (§18, the strict reader row).
- **Which files are listed.** The format folders are listed with the union of the folder layouts of every version the tool supports (format-spec §15.2), so a file at a path that only an older version has (for example a file that a newer version moved or split) is read, reported and migrated, never ignored. Each path takes its kind from the newest version whose layout has it. A file is checked against the schemas of its own version only when that version's layout has its path; otherwise it is `schema-violation` at `/formatVersion` and the file is `invalid`, so it blocks a migration (format-spec §15.3 step 1). At version 1 there is one layout, so this changes nothing until a version changes the layout.
- **Validation** of a parsed file runs its version's schema and the rules within the file, then the cross-file checks run over all parsed files. A file with any error is `invalid`: its value is not used by the index or by other files' checks.

### Writing library files

Every write runs these layers in order. Each layer either passes or ends the write with a result (§3); nothing of the plan touches the disk before layer 8. The gate's recovery and migration (layer 1) are the exception: they write before the plan exists.

1. **Gate** (below): refresh the snapshot, then check the migration backup, newer files and older or mixed versions.
2. **Plan:** `build` returns the file changes from the gated snapshot. A plan may not replace or delete a file whose status is not `valid` (refused with that file's issues): a file with errors may hold the user's words in a form the tool cannot read, for example after a hand-resolved merge, and only the user repairs it, by hand or with a later repair command. The same holds for each file in the plan's `blockedBy`: one that is not `valid` refuses the write with its issues, and one that lies in a folder that could not be listed (so whether it exists is unknown, "Links to files with errors" below) refuses it with that folder's `unreadable-file` issue. A change to a file in such a folder (to replace, delete or create it) is refused the same way, with that folder's issue: whether the file exists is unknown, and a folder that leads outside the library is never written (§4 "Reading library files", "Links stay inside the library"). Every file of the plan is checked, and the issues of all of them are listed.
3. **Authorize** (M3): agent writes are checked against the allowlist (format-spec §13.1) by comparing old and new values; outside it gives `not-allowed`. User writes pass.
4. **Validate** each changed file: the schema and every rule within the file; an invalid change refuses the whole plan, with the issues of every invalid file. Then, on one view of the library with the whole plan applied (deletions included), the **new links** of the files the plan writes. A link is new unless the same holder already linked to the same target in the old value: the holder is the entry with the same id (a term, guardrail, statement or direction) or, for links outside entries, the same field of the same file (a family's `members`, a reference's `result`). So a new term that links to a piece that another term already links to is still a new link. A new link must resolve, otherwise the write is refused with `dangling-link` (severity `warning`, as in format-spec §16.2, but listed among the issues that refused the write). Links that were already dangling are kept, and so are the links that a deletion leaves dangling in files the plan does not change: they are not new. A new link into a file that exists but is not `valid` cannot be checked and is refused the same way, with a message naming that file. Warnings in the new value (`proposal-stale`, `duplicate-term`) do not block.
5. **Canonicalize** the values: round proportions (below), sort lists and order keys as format-spec §3.3 requires.
6. **Timestamps:** the pipeline sets every `updatedAt` itself, so no operation can forget one; operations leave the old `updatedAt` in place (or `createdAt`, for something new). For each file in the plan, the canonical new value is compared with the canonical form of the old value, with every `updatedAt` field set aside; a change that differs in nothing else is dropped from the plan (a deletion always differs). If no change is left, the write ends as `unchanged`, writes nothing and moves no timestamp (so a valid file that is merely not canonical is not rewritten by a write that changes nothing in it). A file that differs gets `updatedAt` = the later of now and its `createdAt`; entries with their own `updatedAt` (terms, guardrails, statements, directions) are compared by id the same way and set the same way. A new file, and a new entry or pin (an id the old value does not have), gets `createdAt` (and `updatedAt`) equal to now, whatever the operation put there; an existing `createdAt` is never touched. The same rule gives `reviewedAt` the later of now and `proposedAt` in the review operations (format-spec §4.1). The clock is an option of `library.write` (default the system clock), so tests fix time and skew; it is read once per write, so every file of a plan gets the same time.
7. **Serialize:** the final value, timestamps included, is validated again as an internal assertion (a failure is a bug and throws), then written as `JSON.stringify(value, null, 2)` plus LF.
8. **Replace** each file, the primary change first (format-spec §5):
   - First, check every target against its snapshot bytes (or its absence), and the migration backup, before anything touches the disk: a change to any of them refuses the whole write with `write-conflict` (`written` empty, `notWritten` every file), and an I/O error fails it the same way. Then the files are replaced or deleted in plan order. A write that stops at a file after that (a conflict in the window, an I/O error) ends `refused` or `failed` with the files before it in `written` and that file and the rest in `notWritten` (the file counts as written when only its folder flush failed); `skipped` is kept in every result.
   - Then create the missing folders (`references/`, `families/`, `projects/<slug>/`, "created when first needed", format-spec §5) one level at a time with a non-recursive `mkdir`, remembering which ones this write created.
   - For each file: write a temporary file `.<name>.tmp-<8 Crockford characters>` in the same folder (created exclusively, `wx`), `fsync` it and close it. Just before the rename, and again before each Windows retry (below), read the target again and compare it, and `lstat` `.tastelib/migration-backup/` again: a different target, or a backup that appeared since the gate (another process started a migration), ends the write with `write-conflict` and deletes the temporary file. Then rename it over the target. A deletion uses the same checks before `unlink`.
   - If the write ends `refused` or `failed`, every folder this write created and left empty is removed again (non-recursive `rmdir`; a folder that another writer has filled meanwhile stays), so a refusal leaves the library as it was, folders included.

   What remains is the short window between the last re-read and the rename, which format-spec §5 accepts.
9. **Update** the snapshot from the bytes written, after each file that reached the disk (a failed flush marked `applied` included): the handle keeps the file's entry built from the bytes written and the check of layer 7, with no fingerprint and marked unsettled (§4 "Index"), or drops it for a deletion, so the next refresh reads it back once instead of trusting a `stat` that another writer may have raced. A refresh that started before the write and ends after it marks that path unsettled too. This is in memory only, so it is not on-disk cleanup.

**Cleanup only on result paths.** On-disk cleanup (deleting a temporary file, removing a folder this write created, a migration cleaning up after itself) runs only where a recognized failure is turned into a result: an error from the file system with an `errno` code, or a failed check. It never runs in a `finally` block or in a catch that rethrows. Any other exception (a bug, or the tests' `SimulatedCrash`, §15 "Core test approach") propagates with nothing cleaned up, exactly like a process that dies at that point, so the crash tests see what a real crash leaves. Closing file handles in `finally` is allowed; it changes nothing on disk.

**Proportions.** Regions are rounded per axis in integer millionths, on values that already passed validation (rounding is not a repair, so a negative width is still refused): `P = round(x × 10^6)`, `S = round(w × 10^6)`; then `S = max(S, 1)` (a tiny width must not become 0), `P = min(P, 10^6 − 1)`, and if `P + S > 10^6` then `S = 10^6 − P` (the clamp keeps the edge); `x = P / 10^6`, `w = S / 10^6`; the same for `y` and `h`. Rounding each value on its own fails twice over: `x = 0.1234565, w = 0.8765435` (sum 1) gives `x + w = 1.000001`, beyond the 1e-9 tolerance (format-spec §7.3), and `w = 4e-7` becomes `0`. The rule guarantees that a valid region never becomes invalid; that it is idempotent; that a valid region whose four values all have at most 6 decimals is never changed (each axis is rounded on its own, and a valid axis whose two values have at most 6 decimals is left as it is, so other writers that keep at most 6 decimals stay canonical); that no value moves by more than 1e-6; and that `JSON.stringify` of `k / 10^6` never prints more than 6 decimals or an exponent. These were checked on 2 million random valid regions, including regions touching the edge, within the tolerance beyond it, and tiny at the far edge. This is a rounding rule within format-spec §3.3, not a format change. `not-canonical` compares a valid file's bytes with the canonical form of its value, rounding included.

**Durability.** Every library write `fsync`s its temporary file before the rename, on every platform. Without it, a power cut after the rename can leave the target empty or truncated on some file systems and mount options (the rename reaches the disk before the data), which would lose the user's words; the cost is one flush per file, while writes come at the pace of a person or an agent. The folder is flushed after the rename (and after a deletion) only in **durable mode**, for the files recovery depends on (format-spec §5, §15.3), and never on Windows: without that flush a power cut can undo the rename, which leaves the previous complete file, a lost recent edit but not a broken file, and only matters where recovery depends on the order of steps. In durable mode the parent of every folder the write created is flushed too, so the new folder's entry survives a power cut. A flush that fails after the rename or removal is a `failed` write marked `applied`: the file counts as written, so a caller that undoes its writes (the migration runner) must undo it as well, and the folders it created stay. The replace primitive creates folders only below the library folder it is given; when that folder is gone the write fails with `io-error` `ENOENT`, which the pipeline turns into the failure `openLibrary` gives for a folder that is gone, `unreadable-folder` (or `not-a-library` when only `library.json` is gone). A flush on macOS is a real flush of the drive cache (`F_FULLFSYNC`), slower than on Linux, so the migration runner flushes only what format-spec §15.3 requires (§18, the `fsync` row).

**Links on the way to a file.** The replace primitive is given the library folder (`root`) by every caller that writes in a library, the migration runner and recovery included. Before it creates a folder, writes a temporary file, renames or deletes, it resolves `root` and the nearest existing folder above the target and checks that the second is the first or lies under it, and, for a target that is not in `.tastelib/`, that it is neither the real `.tastelib/` or `.git/` of the library nor lies under either of them, compared by identity as in §4 "Attaching a media folder", "Comparing folders" (an absent `.tastelib/` or `.git/` is not a refusal) (§4 "Reading library files", "Links stay inside the library"); otherwise the write fails with `io-error` (operation `realpath`, `EINVAL`, "the target's folder leads outside the library folder") and nothing is touched, as for a target outside `root` by its text. Folders it then creates lie under that checked folder, so they are inside too. This guards the window between the listing and the write (a folder replaced by a link meanwhile); the plan is refused earlier with the folder's issue (layer 2). The target itself is never followed: when it is a symbolic link, the rename replaces the link and a deletion removes it, and the file it led to is left as it was. Only the optimistic check reads through it, to compare bytes, and reports nothing of what it read.

**Windows renames and deletions.** On Windows, a `rename` or `unlink` that fails with `EPERM`, `EACCES` or `EBUSY` (a file held open by an antivirus, a sync client, an indexer or an editor) is retried until 2 seconds have passed since the first failure, waiting 10 ms before the first retry and doubling the wait up to 250 ms. Before each retry the optimistic check is repeated: if the target changed meanwhile, the write ends with `write-conflict` and the temporary file is deleted. When the time is up, the write ends with `io-error` naming the operation and the error code, and the temporary file is deleted. If that fails too, the temporary file stays: inside `references/`, `families/` and `projects/`, `validate` reports it as `leftover-temp-file`; at the top level of the library (the temporary file of `library.json`, `glossary.json`, `guardrails.json` or `taste-profile.json`), format-spec §5 ignores other files and `validate` does not report it, so `tastelib doctor` lists it instead (§4 "Command line", the `temp-files` check). On Linux and macOS these errors are real permission problems and are not retried. The platform is an option of the file-system adapter, so the retry path is tested on every CI system.

### Write gate

Before the plan is built, every write checks, in order:

1. **Refresh** the snapshot (§4 "Index"). This is how a write learns the state of the whole library without reading every file each time: a long-running process (the M2 server, the MCP connector) keeps its snapshot and refreshes it with a `stat` scan, re-reading only files that changed; a one-shot CLI command reads every file once when it opens the library, and its write refreshes that snapshot with the same `stat` scan, which re-reads only what changed since. The version summary in the index (each file's `formatVersion` and status) answers the next three checks without another read.
2. **Migration backup:** first, a `.tastelib/` that leads outside the library refuses the write with `unreadable-file` at `.tastelib` (§4 "Reading library files", "Links stay inside the library"), checked on every write like the backup. Then `lstat` of `.tastelib/migration-backup/` on every write, never cached, and again before each rename and each Windows retry (layer 8 above). While it exists, recovery runs first (format-spec §15.3). Until recovery is built, every write gets `write-conflict`.
3. **`library.json`:** missing (or the folder can no longer be read), the write ends `failed` with the same `not-a-library` (or `unreadable-folder`) failure that `openLibrary` returns; present but not `valid`, it is `refused` with that file's issues, because the library's version is then unknown.
4. **A `newer-format` file anywhere** in the library (format-spec §15.1): refused, with one `newer-format` issue per newer file.
5. **An older or mixed library:** migrated on disk (format-spec §15.2–§15.3), then the snapshot is refreshed and the write goes on with a `migrated` notice, which stays in the result whatever happens to the plan afterwards (§3). In the notice `{ code: "migrated", from, to }`, `to` is the current version and `from` is the version of `library.json` when it is older; for a mixed library whose `library.json` is already current, `from` is the lowest version present among the library's files (the index's version summary). A migration that cannot run (a file with errors at step 1, or errors left after the steps at step 3 of format-spec §15.3) writes nothing, and the write is `refused` with the issues of the files that block it; one that fails after its claim ends as described in "Migration runner failures" below. At version 1 no library can be older or mixed, so this path first runs with the test-only step (§15 "Core test approach").

Writes to the media folder have their own guard on the marker (format-spec §6.1, §15.1).

### Migration runner failures

- **The backup copies** (format-spec §15.3 step 4) are made from the files on disk, read again after the claim, never from the bytes held in memory since step 1. Each one is compared with its step-1 bytes; a difference means something changed the file between step 1 and the re-read after the claim, so the runner stops on the path before the manifest exists: it deletes the backup in the order of step 7 (`owner.json` last), and the write is `refused` with `write-conflict` naming that file. No library file has been written at that point, and a backup never holds bytes that were no longer on disk.
- **The runner's own writes** (format-spec §15.3 step 5, and the deletions there) use the same replace primitive, with the bytes it read at step 1 as the expected bytes (absent for added files), and without the backup check, since the backup is its own. Other `tastelib` writers are kept out by the backup, so a mismatch means something outside `tastelib` (a `git pull`, an editor) changed the file during the migration. The runner then stops and cleans up as below, and the write is `refused` with `write-conflict` naming that file; the next write reads everything again and migrates from there. Only the window between a re-read and its rename remains, as for every write.
- **A runner that fails after its claim cleans up its own backup before it returns**, as the owner finishing its own migration (format-spec §15.3 keeps *other* writers out while the owner is alive; the owner itself may finish): an I/O error or a conflict before the manifest exists deletes the backup in the order of step 7 (`owner.json` last), because no library file was written yet; with the manifest `in-progress`, it undoes only what this run did, from the list it keeps in memory: each file it already replaced or deleted is restored from the backup, checked first against the bytes the runner wrote (or against its absence, for a deletion), and each added file it created is removed, checked the same way; every file it had not reached yet, including the one that conflicted, is left untouched. Restores and removals are durable as in recovery case 7. Then it deletes the backup; with the manifest `done`, it deletes the backup. The write then ends `failed` (`io-error`) or `refused` (`write-conflict`), and the library is as it was before the migration (or migrated, if `done` was reached). This runs only on these result paths (§4 "Writing library files", "Cleanup only on result paths").
- **If that cleanup fails too** (the disk is still failing, or a restore meets a file changed meanwhile), the backup stays, with this process as its live owner. A file whose bytes are neither those the runner wrote nor the backup's (something else changed it meanwhile) is left as it is. Other processes treat it as live (case 3) until this process ends, as format-spec §15.3 requires. So that a long-running process (the M2 server, the MCP connector) does not block its own writes for as long as it runs, it remembers, in memory, the backup it failed to clean up and the exact bytes of the `owner.json` it wrote; before its next write it resumes that cleanup as the owner, but only if `owner.json` still holds exactly those bytes. A resumed cleanup accepts, for each file of its list, exactly two states: a file the runner replaced holds the runner's bytes (restore it from the backup) or the backup's bytes (already restored); a file the runner deleted is absent (restore it from the backup) or holds the backup's bytes (already restored); a file the runner added holds the runner's bytes (remove it) or is absent (already removed); a file in any other state stops the resumed cleanup, the backup stays, the write is `refused` with `write-conflict`, and the user resolves it with `tastelib doctor --resolve-migration`. Otherwise, and once the process has ended, the recovery cases of format-spec §15.3 apply as usual, and `tastelib doctor` reports a backup that stays stuck.

### Links to files with errors

A cross-file link resolves if its target file is `valid` and holds the target (the reference and its piece `p0` or a pin; the family; the project and its direction; the guardrail). It is dangling if the target file is absent, or `valid` without the target. A link into a file that exists but is not `valid` (`invalid`, `unreadable` or `newer`) is **unresolved**: `validate` reports no `dangling-link` for it, because whether the target exists cannot be known and the broken file already has its own error, the one to fix; the index counts it for nothing (a broken family gives its pieces no family); a write that adds such a link is refused (layer 4 above); and link removal after a deletion skips files that are not `valid` and still writes the deletion, and the `written` result lists each skipped file in `skipped` with the reason (`{ path, reason: "invalid" | "unreadable" | "newer" }`), so an unrelated broken file never blocks the user's decision. A format folder that could not be listed and may hold files with links to the deleted thing (`families/`, `projects/` or a project's folder, `references/`) is skipped the same way and listed in `skipped` as `{ path: <folder>, reason: "unreadable" }`. A link that is still there shows up as `dangling-link` once that file is repaired. The file that holds the thing being deleted is different: when it is not `valid`, or lies in a folder that could not be listed, whether the thing exists is unknown, so the deletion is refused with that file's (or folder's) issues (`blockedBy`, layer 2) instead of being taken for already done.

### Index

The index is derived data, kept **in memory only**, inside the snapshot; nothing is cached under `.tastelib/`, so deleting `.tastelib/` (outside an interrupted migration) can never make it wrong.

- **What it holds** (M2–M4): every file's kind, fingerprint, `formatVersion` and status, and a version summary (the library's version, the versions present, whether any file is newer, whether versions are mixed); every reference with its pieces (`p0` and its pins), its derived state (inbox, processed, reviewed, format-spec §7.7, a rejected interpretation counting as reviewed, §13.3) and its `result` link; the families of each piece, derived from `members`: a family whose description has no effective value, or a rejected link, gives nothing, and a `to-review` description or link gives a tentative family; the existence sets the dangling checks use (references and their pieces, families, projects and their directions, guardrails); and backlinks: for each link target, every `(file, pointer)` that links to it, for link removal and for showing where something is used. Each later milestone adds the views it needs (the review queue in M3, browsing in M4) as pure functions of the parsed files.
- **Where each part lives.** Each file's kind, fingerprint, `formatVersion` and status live in the snapshot's `files`; the index (`snapshot.index`) holds everything else and does not copy them. The existence sets are about files: a family file whose description is rejected still exists for the dangling check (format-spec §14), and effective values decide only which families are listed and which families a piece has. A member whose target is dangling or unresolved counts for nothing, like a rejected one. Backlinks list every link that the cross-file checks see, dangling and unresolved ones included (link removal needs them), in path order and then in file order, grouped by target and, for pieces, by reference, so a link to a pin that is gone is still found. The cross-file checks and the index resolve links by one rule and read the versions from one summary, so they cannot disagree. In an older or mixed library the index (everything but the per-file data and the version summary, which come from the files on disk) is built from the snapshot's `migrated` view (§3), with its paths, so links, families and backlinks work for read-only commands before the first write. When `migrated` is `null` (the migration cannot run), only files valid at the current version hold links or are indexed. No write relies on `migrated`: the write gate migrates the library on disk first (§4 "Write gate").
- **How it is built.** Work per file (read, parse, validate against the file's own version) is cached by fingerprint and redone only for changed files. Everything library-wide (the in-memory migration of an older or mixed library, which works on the whole library because a step may add, move or remove files, format-spec §15.4; cross-file checks, derived states, families, backlinks) is recomputed from the parsed files after every change, since it costs about 10 ms for 5000 references. So an updated index is always a fresh rebuild from the same parsed files, and there is no incremental update that could drift.
- **Freshness.** Before any answer, and before every write, a refresh lists the format folders and `stat`s every file. The fingerprint is `(size, mtime, ctime, inode)` from `stat` with `bigint: true` (nanoseconds where the file system has them). A listed name that is new, gone or has a different fingerprint is re-read. A file is kept **unsettled** when `0 ≤ statTime − mtime < 3 s`, `statTime` being the system clock when it was stat'd (an `mtime` in the future, for example from a sync tool that keeps another computer's times, does not count): the next refresh reads it again and compares bytes, whatever its fingerprint, because a second change within the file system's timestamp resolution (2 seconds on FAT) could keep size and `mtime`. A request is answered from a refresh that started after the request arrived; requests that arrive together share one refresh. A file that is read again takes as its fingerprint the `stat` of the handle that read it, taken before the read, never a `stat` after it, which could pair new metadata with old bytes; its `statTime` is the clock right after that read. With nothing changed (the same paths, the same file entries, the same listing issues and unlisted folders), a refresh returns the previous snapshot itself; otherwise everything library-wide is recomputed from the file entries.
- **No `fs.watch`** in M1. Node documents it as "not 100% consistent across platforms" and unreliable on network file systems and in virtual machines; a sync folder or a `git pull` would be missed silently. The M2 server may add it only as a hint to push "library changed" to the interface, never as the reason to skip a refresh.
- **Performance budget**, checked by a test on Linux, Windows and macOS CI, on a library generated at test time with a fixed seed: 5000 references (1–2 media items, 0–5 pins, about 60% of pieces interpreted, about 3.4 KB per file), 50 families of 100 members, 300 glossary terms and one project, about 17 MB in all:
  - opening it (read, parse, validate every file, cross-file checks, index) **under 5 seconds**;
  - refreshing it when nothing changed **under 0.5 seconds**, and when one reference changed, with the index updated, **under 0.5 seconds**;
  - one single-file write on the open library, gate and `fsync` included, **under 1 second**.

  The budget is promised for the computers the tool is used on. On a CI runner, a line also passes when it stays within a bounded overhead over a baseline measured in the same run, on the same files, just before the line (maintainer decision, §18): opening within `k` times a plain read and `JSON.parse` of every file (16 reads in flight) plus a fixed overhead; a refresh within `r` times a plain `stat` of every file (16 in flight) plus a fixed overhead; one write within `w` times that `stat` scan plus one plain write of the same size with `fsync` and rename, plus a fixed overhead. A line fails only when it misses both its absolute budget and its relative bound, so a runner slower than those computers passes as long as the code adds no more than the bound over what the runner itself costs, and a change that makes the code itself slower still fails. The factors and overheads are named constants in the budget test, the same on every system, set from the timings of a CI run on Linux, Windows and macOS (§15 "Core test approach"). Factors per platform and a wider absolute budget are rejected (§18).

  **Three runs, the fastest checked** (maintainer decision, §18). Each line, and each of its baselines, is timed three times, one after the other, and the fastest run is the one checked against the absolute budget or the bound. Noise on a shared runner only adds time, so the fastest run is the fair measure of the code, while a real regression (a step that becomes quadratic, say) shows in all three. The rule above does not change: absolute budget **or** bound over the baseline. Making the budget report-only on a platform is not part of this decision.

  The budget test runs alone, after every other test file of `core`, because a timed line that shares the runner's CPUs with other test files measures them too (§15 "Core test approach"). Reading every file once per CLI command is acceptable at this size. If the budget fails, or the M2 checkpoint shows CLI commands are too slow, the first remedy is a cache under `.tastelib/` keyed by the same fingerprints (still disposable), decided then; a synchronous `stat` scan is not taken, because it blocks the event loop of the M2 server (§18).

### Command line

`tastelib` (`packages/cli`) is the command people and agents run. M1 delivers `init`, `validate`, `doctor` (with `--resolve-migration`), `migrate` and `config`; later milestones add commands (`open` in M2, the agent writes in M3, `export` in M5) under the same rules. What a command does to library files belongs to `core` (above), and so does everything that the app (M2) or the MCP connector (M3) will also need: the command line only parses, calls `core` and prints. This part fixes what each command accepts, checks, writes, prints and returns. The report of `validate` is format-spec §16; everything else here is the command line's own contract.

Three maintainer decisions (2026-11-04) are settled and not reopened here: `init` does not run `git init` unless asked with `--git`; a media folder inside the library folder, and a non-empty folder without the marker, are refused with no exception, each with a message that explains why and what to do; the text output is English only in M1, every error has a stable code, and every command has `--json` output for agents.

#### Building and running

- The command is the `bin` of `packages/cli` (`tastelib` → `dist/bin.js`). It checks the Node version against the minimum of `engines.node` (26.13.0) before it loads anything else, so an older Node gets `node-too-old`, never a syntax error. `packages/cli/package.json` has its own `engines` field, equal to the root one (`"node": ">=26.13.0"`), because the root `package.json` is not part of the package that runs; a unit test fails when the two differ.
- The command never cuts off its own output: it sets the exit code and lets the process end instead of calling `process.exit()`, and an `EPIPE` on standard output (the output was piped into a program that stopped reading) ends the command quietly.
- `--version` prints the version of the `cli` package, read at run time, never copied into code.
- **Before any release**, a developer runs `pnpm build`, then `pnpm tastelib <arguments>` from the repository root (a root script `"tastelib": "node packages/cli/dist/bin.js"`; pnpm passes every argument after the script name through, `--help` included), or `node <repository>/packages/cli/dist/bin.js <arguments>` from any folder. pnpm runs scripts in the repository root, so relative paths given to `pnpm tastelib` are resolved from there; use absolute paths with it, or the `node` form. Putting `tastelib` on `PATH` (a linked or released package) is decided with distribution in M7 (§18, the build row).
- **Tests** run the built command as a child process with `process.execPath`, never `tastelib` from `PATH`, never a `.cmd` shim, never a shell: quoting differs per system. Each test builds its environment from scratch: the config folders (`XDG_CONFIG_HOME`, `APPDATA`) point to a fresh non-ASCII temporary folder, so no test reads or writes the developer's own config, and `NO_COLOR` is unset unless the test is about colors. A test that needs `git` to be missing sets `PATH` to an empty folder, after removing every case variant of the variable (Windows has `Path`). The `cli` tests build first, so `dist/` is current. What needs test-only dependencies (the test migration step, injected crashes, a terminal for prompts) runs the command in process with fakes; the child-process tests cover what only a real process shows: exit codes, the two output streams, the version guard, `git`.

#### Arguments

- Parsing uses `node:util` `parseArgs`; no dependency. The first argument is the command (`config` takes a second one, its action). Each command has its own options and checks them itself, so every usage error has a code from the list below and a message of ours, never Node's own text, which can change between Node versions:
  - an option the command does not have: `unknown-option`;
  - no command, an option without its value, or a required option or argument missing: `missing-argument`;
  - an extra positional argument, a value given to a flag (`--json=1`), or an option given twice: `unexpected-argument`;
  - a value that breaks its rule (a name, a language tag, a config key): `invalid-argument`, with the argument it concerns.

  Every usage error exits 2 (format-spec §16.1), and its text message ends with "Run `tastelib <command> --help`."
- A value that starts with `-` is written `--name=-value`; `--name -value` is refused (`missing-argument`), because it usually means a forgotten value. `--` ends the options, so a folder named `-x` can be given after it.
- `--help` (or `-h`) prints the command's help on standard output and exits 0, whatever else is on the line; `tastelib --help` lists the commands. `tastelib --version` prints the version and exits 0. Help is text only, for people, even with `--json` (the one exception, "Output" below). `tastelib` with no command prints a short usage on standard error and exits 2 (`missing-argument`); an unknown command exits 2 with `unknown-command` and the list of commands.
- No negative flags (`--no-…`) and no short forms except `-h`.
- A path given on the command line is resolved against the current folder with `path.resolve`, which removes `.` and `..` segments by their text and keeps symbolic links as given. A path the command stores in the config is that string, never resolved with `realpath` and never Unicode-normalized (§13).

#### Which library a command uses

`validate`, `doctor`, `doctor --resolve-migration` and `migrate` work on one library, chosen in this order:

1. The `<library>` argument. It must be a library folder itself (no search upward); otherwise `not-a-library`, naming the folder.
2. The current folder, or the nearest folder above it with a `library.json`, searched on the real path (symbolic links resolved) up to the root. A command run anywhere inside a library uses that library, as Git does with its working tree. A `library.json` is passed over, and the search goes on upward, in one case only: the strict reader (§4 "Reading library files", within the 8 MiB limit) parses it into a JSON object that has no `id` matching `LibraryId` (format-spec §4.3), which is clearly another tool's file. Every other `library.json` stops the search and its folder is used: a file that does not parse (a damaged one, a merge left unresolved), a value that is not an object, a file that cannot be read or is too large (including one that is a link leading outside its folder, which is not read, §4 "Reading library files", "Links stay inside the library"), an entry of that name that is not a regular file, and of course a file with a valid `id`. So a command run inside a library whose `library.json` is damaged checks that library, and `validate` reports its errors (exit 1), instead of silently checking the configured one. (`init` is stricter still: any `library.json` in or above the folder refuses it, because format-spec §5 makes any folder with that file a library.)
3. `libraryPath` from the config. It must be a library; otherwise `not-a-library`, naming the field and the config file.
4. Otherwise, for `validate`, `migrate` and `--resolve-migration`, `no-library` (exit 2): "No library found. Give a library folder (for example `tastelib validate <folder>`), run the command inside one, or set the library of this computer with `tastelib config set libraryPath <folder>`. To create one, run `tastelib init`."

`doctor` never stops on these: a missing library, or an argument or `libraryPath` that is not a library, is reported by its `library-path` and `library` checks (status `warn`, `fail` or `skip`, with the same codes), and the other checks run.

The current folder comes before the config so that someone working in a second library (a copy, a test library) is never sent to the configured one without noticing; an agent working in a project folder outside any library gets the configured one. The text output of `validate`, `doctor`, `migrate` and `--resolve-migration` names the library and where it came from (argument, current folder or `libraryPath`), so a person always sees which library was checked. For `validate` this is in the text output only, and without an absolute path that the user did not type (§14): the argument as typed, the folder found from the current folder written relative to it (`.`, `..`, `../..`), or "libraryPath from the config"; `validate --json` at exit 0 and 1 stays exactly the format-spec §16.3 report, with no field added and no absolute path (§14).

**The media folder** of a command is `--media <folder>` when given (only `validate` has it); otherwise `mediaPath` from the config, but only when the library in use is the configured `libraryPath` (the same folder, compared as in "Attaching a media folder" below), because `mediaPath` is that library's media folder; otherwise none, and `validate` reports `media-not-checked`. Using `mediaPath` for whatever library is in use would report another library's media folder as `media-folder-mismatch`, an error, for a library that has no fault.

**The config is read only when a command needs a value from it**, so `tastelib validate <folder> --media <folder>` runs even when the config file is broken, which CI and tests rely on. When a value is needed and the file cannot be read or is invalid, the command exits 2 with `config-error`, the file and the field of the `ConfigError` (§4). `doctor` reports it as a check instead.

#### `tastelib init`

`tastelib init [<folder>] --name <name> --language <tag> [--git] [--json]`

- `<folder>` defaults to the current folder. If it does not exist, it is created, but only when its parent exists (otherwise `parent-folder-missing`), so a mistyped path, or a sync folder whose client is not running, never grows a tree of new folders.
- `--name` (required) is the library's name, the user's words (format-spec §13.1: `tastelib init` writes it). It is stored exactly as given and never trimmed or altered. If it is not a valid `Name` (format-spec §4.2: 1–200 code points, one line, no control characters, well-formed Unicode), it is refused with `invalid-argument` and the rule it breaks, for example "--name contains a control character (U+000A) at position 12; a name is one line without control characters." A line break is refused like any other control character.
- `--language` (required) is the `LanguageTag` in which agents write proposals (format-spec §5.1), for example `en` or `pt-BR`; a tag that does not match the pattern is refused with `invalid-argument`. It has no default: no command in M1 changes `library.json` afterwards, so a wrong default could be fixed only by editing the file by hand, and the interface language is a different, per-machine setting (§12).
- `--git` runs `git init` (Git, below).

**Checks, in this order, before anything is written.** Each refusal exits 2 and leaves every file and the config as they were.

1. The arguments (above).
2. The folder: a path that exists and is not a folder gives `not-a-folder`; a folder that does not exist, in a parent that does not exist either, gives `parent-folder-missing`.
3. Walking up the real path of the folder (or of its parent, when the folder does not exist yet):
   - `library.json` in the folder itself: `already-a-library` — "<folder> is already a library (it has library.json). Nothing was changed. To use it on this computer, run `tastelib config set libraryPath <folder>`."
   - `library.json` in a folder above it: `inside-library` — "<folder> is inside the library at <library>. A library cannot hold another library: its files would end up in that library's folder and Git history. Choose a folder outside it."
   - `tastelib-media.json` in the folder or above it: `inside-media-folder` — "<folder> is inside the media folder at <media>. A library must not live in a media folder: the library belongs in Git and media must stay out of it. Choose a folder outside it."
4. Library files without `library.json` (`references/`, `families/`, `projects/`, `glossary.json`, `guardrails.json` or `taste-profile.json` in the folder): `library-files-present` — "<folder> already holds library files (for example references/) but no library.json. It may be a library whose library.json was lost: restore that file from Git history instead of creating a new library, which would get a new id and no longer match its media folder."
5. An existing `.gitignore` that is not a regular file, is larger than 1 MiB or is not UTF-8: `gitignore-unusable`.
6. The config is read, because it decides `libraryPath` below; `config-error` stops here.
7. A configured `mediaPath` that is the folder or inside it (compared as in "Attaching a media folder"): `media-inside-library` — "The media folder <media> set in the config is inside <folder>. A library must not contain a media folder: the library is committed to Git, and media must never be. Choose a folder that does not contain the media folder."
8. With `--git`, the Git checks below.

**What it writes, in this order:**

1. The folder, when it is missing (one non-recursive `mkdir`).
2. `.gitignore`. When there is none, it is created with two lines, `# Working area of taste-library, never committed` and `.tastelib/`. When there is one and no line in it already ignores the folder (a line that is exactly `.tastelib/`, `.tastelib`, `/.tastelib/` or `/.tastelib`, ignoring trailing spaces and a CR), the line `.tastelib/` is appended, after a line break if the file does not end with one, and with CRLF if the file's first line break is CRLF; nothing else in the file changes. It is replaced atomically with the optimistic check (§4 "Writing library files", layer 8), without durable mode.
3. `library.json`: a new `LibraryId`, the name, the language and `createdAt` from the clock, validated against the v1 schema, serialized canonically and written with the same atomic replace, expecting no file. It does not go through `library.write`: the write pipeline needs an open library, and there is none yet. If another `init` created the file meanwhile, the replace's `write-conflict` is reported as `already-a-library`. `library.json` is written last because it is what makes the folder a library: when anything before it fails, running `init` again works, and an existing `.tastelib/` line is not added twice.

Folders such as `references/` are created when first needed (format-spec §5), so `library.json` is the only format file `init` writes. A library created by `init` passes `tastelib validate --strict` (without a media folder its only report is `media-not-checked`, an info).

**Git** (maintainer decision). The Git working tree of the folder is found as `assertMediaOutsideGit` finds it (§4): a `.git` folder or file in the folder or any folder above, on the real path. Without `--git`, `init` never runs `git`:

- no working tree: the notice `suggest-git-init` — "This folder is not in a Git repository. A library is usually its own private repository, so that its history can undo mistakes and migrations: run `git init` in <folder>, then commit.";
- the folder is inside another repository's working tree (`.git` above it): the notice `in-git-working-tree` — "This library is inside the Git working tree at <worktree>; its files will be committed to that repository.";
- `.git` in the folder itself: nothing to say.

With `--git`:

- `.git` already in the folder: `git init` is not run, and the notice `git-already-initialized` says so.
- `.git` in a folder above: refused before anything is written with `git-nested-repository` — "<folder> is inside the Git working tree at <worktree>. --git would create a repository inside a repository, which Git handles badly. Run `tastelib init` without --git to keep the library in that repository, or choose a folder outside it."
- Otherwise `init` first resolves `git` to an absolute path itself: it looks for `git` in each entry of `PATH`, in order, and takes the first that is a regular file and, on Linux and macOS, executable by this user (`access` with `X_OK`, so a non-executable file named `git` earlier on `PATH` does not hide a working one further down); on Windows it looks for `git.exe` as a regular file. It goes through the entries skipping every entry that is not an absolute path, and never looks in the current folder or the folder being initialized. It never spawns `git` by name: libuv's search on Windows looks in the child's working folder first, and a relative `PATH` entry (or an empty one, which means the current folder) does so on every system, so a `git.exe` planted in the new library folder could run (§14). No match refuses before anything is written with `git-not-found` — "--git needs Git, which was not found on this computer. Install Git, or run `tastelib init` without --git and run `git init` later." Then it runs `<absolute path> --version` (no shell); a spawn error or a non-zero exit is `git-not-found` too.
- After the files are written, `<absolute path> init` runs in the library folder (`cwd`, no shell, its output captured and not printed). A non-zero exit or a spawn error gives `git-failed` (exit 2) with Git's first error line: "The library was created, but `git init` failed: <line>. Run `git init` in <folder> yourself." Because `.gitignore` is written first, the new repository ignores `.tastelib/` from its first commit. `init` never commits.

**The config.** When the config has no `libraryPath`, `init` sets it to the new folder through `writeConfig`, so a first library works from any folder at once. When `libraryPath` is already set, it is kept, so a second or test library never replaces the configured one silently, and the notice `library-path-kept` says "libraryPath still points to <path>. To use the new library on this computer, run `tastelib config set libraryPath <folder>`." When `init` sets `libraryPath` while `mediaPath` is already set (left over from an earlier library), `mediaPath` belongs to another library (the new one has a new id), so `init` keeps it and adds the notice `media-folder-of-other-library`, exactly as `config set libraryPath` does. A config write that fails after the library was written gives `config-error` (exit 2), and the message says that the library was created.

**No media folder in the same step.** `init` does not attach a media folder: attaching has its own refusals (below), and one command that half-succeeds is harder to understand and undo than two that each succeed or change nothing. When `init` set `libraryPath`, its text output ends with the next step: "Next: create an empty folder outside the library for media, then run `tastelib config set mediaPath <folder>`."

**Order of the steps after the checks:** the files, then `git init` (with `--git`), then the config, then the notices.

#### `tastelib config`

`tastelib config [show] [--json]` · `tastelib config set <key> <value> [--json]` · `tastelib config unset <key> [--json]`

- **`show`** (the default action) prints the path of the config file, whether it exists, and every field: set values as stored, the others as "not set". It never creates the file or its folder.
- **`set` and `unset`** change one field through `writeConfig` (§4: validated, then replaced atomically). In M1, `set` accepts `libraryPath` and `mediaPath`; `language` (the interface's, M2) and `packsExportPath` (M5) are set by the app or added here by their milestones. `unset` accepts all four keys, removes the field and never touches a folder or a marker. Any other key gives `invalid-argument`.
- **A broken config is never overwritten:** when the file cannot be read or is invalid, `set` and `unset` exit 2 with `config-error`, naming the file and the field so the user can fix or delete it. Writing a fresh file over it would silently drop the user's other settings.
- **`set libraryPath <folder>`:** the folder must be a library (`library.json` in it; otherwise `not-a-library`). When `mediaPath` is set and its marker names another library, the notice `media-folder-of-other-library` says "mediaPath points to the media folder of another library (<id>). Attach this library's media folder with `tastelib config set mediaPath <folder>`." `mediaPath` is never changed implicitly.
- **`set mediaPath <folder>`** attaches the folder to the library at `libraryPath`, never to the one in the current folder: the config holds one pair, a library and its media folder. `libraryPath` must therefore be set first (`library-path-not-set`: "Set the library first with `tastelib config set libraryPath <folder>`, then attach its media folder.") and be a library whose `library.json` is valid, since the marker records its id (otherwise `not-a-library`; `library-json-invalid` with that file's issues; or `newer-format`). The folder is then attached (below), and only when that succeeds is `mediaPath` written. A refusal changes neither the config nor the folder.

#### Attaching a media folder

`attachMediaFolder` in `core` is the only code that attaches a folder: `tastelib config set mediaPath` uses it, and so will the app. It runs these checks in this order. The first that fails refuses with its code (exit 2 on the command line) and its message, and nothing is written, neither in the folder nor in the config:

1. **Not a folder:** the path exists and is not a folder: `not-a-folder` — "<folder> is not a folder. Choose or create an empty folder for media."; a link to a folder that does not exist (for example a drive that is not mounted) is the same code, with "<folder> is a link to a folder that does not exist. Choose or create an empty folder for media."
2. **Inside the library folder** (maintainer decision), including the library folder itself: `media-inside-library` — "<folder> is inside the library folder <library>. Media must stay out of the library's folder: the library is committed to Git, and media (captures of other people's work, large files) must never be. Choose or create an empty folder outside the library folder, for example next to it."
3. **Containing the library:** `library-inside-media` — "The library folder <library> is inside <folder>. A media folder must not contain the library: the library's files would be mixed with the media and synced with them. Choose a folder that does not contain the library."
4. **Inside a Git working tree** (§4): `media-inside-git` — "<folder> is inside the Git working tree at <worktree>. Media must live outside every Git repository: the repository would grow with every capture, and captures of other people's work could be committed and published. Choose or create an empty folder outside any repository." This check comes after the library ones because a library is usually a repository, and "inside the library folder" is then the more useful message.
5. **The marker**, when `tastelib-media.json` exists:
   - it cannot be read or is invalid: `media-marker-unreadable`, with the marker's issues (`file: "media:tastelib-media.json"`) — "The marker tastelib-media.json in <folder> is damaged: <first issue>. Restore it from your sync service or another computer, or choose another folder.";
   - another library's id: `media-folder-mismatch` (format-spec §16.2) — "<folder> is the media folder of another library (<id>). Two libraries must not share a media folder. Choose this library's media folder, or an empty folder.";
   - a newer version: `newer-format` — "The marker in <folder> was written by a newer tastelib (marker format <n>; this version supports up to <m>). Update tastelib, then attach it again.";
   - this library's id: the folder is attached again, an older marker is migrated on disk now (format-spec §15.1), and the notice `media-already-attached` says so.
6. **Not empty and without a marker** (maintainer decision): `media-folder-not-empty` — "<folder> is not empty and has no tastelib-media.json marker, so it is not a media folder of this library. tastelib does not take over a folder that holds other files, such as a downloads or pictures folder: it would then report and manage files that are not its own. Choose or create an empty folder, or move this folder's files out first. If this is your media folder and only its marker was lost, attach an empty folder and move the reference folders into it." "Empty" is defined below; there is no exception (maintainer decision).
7. **Parent missing:** the folder does not exist and neither does its parent: `parent-folder-missing`, as for `init`.

Then the folder is created when missing (one non-recursive `mkdir`) and the marker `{ "formatVersion": 1, "libraryId": "<id>" }` is written canonically, with the atomic replace and the optimistic check against the bytes read (or against no file). An I/O failure is `io-error`, with `file` `media:tastelib-media.json` (or `media:` for the folder; `library:` when the failure was in the library folder's side of a comparison). When the marker changed between the read and the replace (the optimistic check fails), the result is a refusal with `write-conflict` and nothing is replaced; `guardMediaWrite` returns the same, and the caller reads again and retries.

**Comparing folders.** "Inside" and "the same folder" are decided on real folders. The media path (or its nearest existing ancestor) is resolved with `realpath` (the native one, as in `assertMediaOutsideGit`, which resolves symbolic links, Windows junctions and mapped drives); then every folder from it up to the root is compared with the library folder by identity: `dev` and `ino` from `stat` with `bigint: true` (on Windows, the volume serial number and the 64-bit file id). So differences of letter case (Windows, macOS), of Unicode normalization (macOS, §13) and Windows short names never matter. Where the file system reports no identity (`ino` is 0, as on some network shares), the real paths are compared after `normalize("NFC")`, case-insensitively on Windows and macOS. `library-inside-media` is the same walk from the library's real folder against the media folder. The Git check walks the same real path looking for `.git`.

**Empty.** A folder is empty when each entry in it has one of the names below (compared after `normalize("NFC")` and `toLowerCase()`, whatever the entry's kind). These are the files and folders an operating system, a file manager or a sync client puts in a folder by itself, and none holds the user's files:

- created by file managers: `.DS_Store`, `.localized` and `Icon\r` (macOS), `desktop.ini` and `Thumbs.db` (Windows), `.directory` (KDE);
- created by sync clients to mark a synced folder: `.dropbox`, `.dropbox.attr` and `.dropbox.cache` (Dropbox), `.stfolder` (Syncthing);
- created by the operating system at the root of a drive, so that a whole drive can be a media folder: `System Volume Information`, `$RECYCLE.BIN`, `.Spotlight-V100`, `.fseventsd`, `.Trashes`, `.TemporaryItems`;
- the temporary file of an interrupted marker write (`.tastelib-media.json.tmp-<8 Crockford characters>`).

Any other entry makes the folder not empty, including other hidden files, an empty subfolder and a symbolic link. The list is closed and short on purpose: a general rule such as "hidden files do not count" would accept a folder holding `.git` or `.config`. Attaching never changes or removes these entries. A folder that cannot be listed gives `io-error`.

**A media folder that lost its marker** (in a sync conflict, or media copied by hand) is not empty, so it is refused like any other non-empty folder without a marker. The way back is to attach an empty folder (which gets a new marker) and move the reference folders (`<ref-id>/`) into it; the media files keep their paths relative to the media folder, so the library needs no change.

#### `tastelib doctor`

`tastelib doctor [<library>] [--json]` checks this computer's setup and writes nothing: it never creates the config, a folder or a marker, never migrates anything on disk (not even the media marker), never recovers a backup, and never runs `git`. Every file it looks at is left unchanged.

Each check has a stable `id`, a `status` (`pass`, `info`, `warn`, `fail` or `skip`), a `code` (for any status but `pass` and `skip`), a `message` and, unless it passes, a `hint` saying how to fix it. A check that reports a format-spec §16.2 code takes the status of that code's severity (error → `fail`, warning → `warn`, info → `info`), so a code never changes meaning between commands. A check whose input is not known (no config, no library, a media folder that belongs to another library) is `skip`, with the reason. The library checks use the library chosen as above; the media checks that concern a library (`media-outside-library`, `media-marker`) run only when that library is `libraryPath` (the media-folder rule above) and are `skip` otherwise.

| Check | What it looks at | Results | Fix hint |
| --- | --- | --- | --- |
| `node` | `process.versions.node` against `engines.node` | `pass`; `fail` `node-too-old` | Install Node.js 26.13.0 or later. |
| `config` | the config file (§4): its path can be found, it can be read and it is valid | `pass`, with its path; `warn` `config-missing` (no file yet, the defaults apply); `fail` `config-error`, with the field | Missing: set the folders with `tastelib config set`. Broken: fix the named field, or delete the file and set the folders again. |
| `library-path` | `libraryPath` in the config | `pass`; `warn` `library-path-not-set`; `fail` `not-a-library`, `unreadable-folder`; `skip` when the config fails | `tastelib config set libraryPath <folder>`, or `tastelib init` to create one. |
| `library` | the library this command uses and where it came from | `pass`, with its path and source; `fail` `not-a-library`, `unreadable-folder` (the argument or `libraryPath` is not a readable library); `skip` when there is none | Give a library folder, or fix `libraryPath`. |
| `library-format` | `library.json` and the versions of the files (the index's version summary, §4 "Index") | `pass` (current); `info` `needs-migration`; `warn` `mixed-format-versions`; `fail` `library-json-invalid` with its issues, `newer-format` | Older or mixed: `tastelib migrate` (or let the next write do it). Newer: update `tastelib`. Invalid: `tastelib validate`, then repair the file. |
| `migration-backup` | `.tastelib/migration-backup/`, through `core`'s read-only inspection of the backup | `pass` (none); `warn` `migration-in-progress` (owner alive on this computer, format-spec §15.3 case 3); `warn` `migration-interrupted` (owner gone: cases 5–7, which the next write recovers by itself); `fail` `migration-backup-stuck` (no or unreadable `owner.json`, an owner on another host, an unreadable manifest: cases 1, 2 and 4) | In progress: wait for it; if no `tastelib` is running (a reused process id), `tastelib doctor --resolve-migration`. Interrupted: `tastelib migrate` recovers it now. Stuck: `tastelib doctor --resolve-migration`. Always: never delete the folder by hand. |
| `temp-files` | temporary files left by an interrupted write: at the top of the library (`.<name>.tmp-<random>` of `library.json`, `glossary.json`, `guardrails.json`, `taste-profile.json`, `.gitignore`), in the format folders (`validate`'s `leftover-temp-file`), at the top of the media folder (the marker's) and in the config folder (`.config-<hex>.tmp`, `writeConfig`'s) | `pass`; `warn` `leftover-temp-file`, with the files (library-relative, `media:` or a name in the config folder) | Left by an interrupted write; the file it was replacing is intact. When no `tastelib` is running, check that none holds an edit you want to keep, then delete them. |
| `gitignore` | `.gitignore` of the library ignores `.tastelib/` (the line rule of `init`) | `pass`; `warn` `gitignore-missing-tastelib` | Add the line `.tastelib/` to `.gitignore`. |
| `git` | the library is in a Git working tree (a `.git` found as `init` finds it) | `pass`; `warn` `library-not-in-git` | Run `git init` in the library folder and commit, so its history can undo mistakes and migrations. |
| `media-path` | `mediaPath`: set, present, a folder | `pass`; `warn` `media-path-not-set`; `fail` `media-folder-missing`, `not-a-folder`; `skip` when the config fails | Not set: attach one with `tastelib config set mediaPath <folder>`. Missing: connect the drive or start the sync client; otherwise attach another folder. |
| `media-outside-git` | `mediaPath` outside every Git working tree | `pass`; `fail` `media-inside-git` | Move the media folder out of the repository, then attach it again. |
| `media-outside-library` | `mediaPath` neither inside the library folder nor containing it (compared as in "Attaching a media folder") | `pass`; `fail` `media-inside-library`, `library-inside-media` | Move the media folder next to the library, then attach it again. |
| `media-marker` | the marker: present, valid, this library's id, a supported version | `pass` (an older marker passes too: it is migrated when the folder is next attached or written to); `warn` `media-marker-missing`; `fail` `media-folder-mismatch`, `media-marker-unreadable`, `newer-format` | Missing: attach an empty folder with `tastelib config set mediaPath <folder>` and move the reference folders into it (a non-empty folder without a marker is refused). Another library's: attach this library's own folder. Newer: update `tastelib`. |

The checks run and are listed in this order. `migration-backup` details hold what that inspection returns: the state (`in-progress`, `done`, `no-manifest`, `unreadable-manifest`), the owner (process id, host name, claim time, and whether that process looks alive on this computer, or unknown on another host) or why it is missing, the files a restore would put back and remove, and any leftover `owner.json.taken-*` file. Its text output always points to `tastelib doctor --resolve-migration` for a backup that stays.

**Exit code:** 0 when no check fails (`info` and `warn` do not fail), 1 when at least one check fails, 2 only when `doctor` itself cannot run (bad arguments).

#### `tastelib migrate`

`tastelib migrate [<library>] [--dry-run] [--json]` migrates the library on request (format-spec §15.2).

- **Without `--dry-run`** it runs the write gate (§4 "Write gate") with no plan: it refreshes, resolves a migration backup first exactly as before any write (format-spec §15.3 recovery), checks `library.json` and newer files, and migrates an older or mixed library on disk.
  - Current, and no backup: "The library is at format version <n>, the current one. Nothing to migrate." Exit 0, and nothing is written: no file, no folder, not even `.tastelib/`.
  - Migrated: "Migrated the library from format version <n> to <m>: <x> files changed, <y> added, <z> removed.", then one line per file (`changed`, `added`, `removed`, then the library-relative path), sorted by path. Exit 0.
  - A recovery ran first: the notice `migration-recovered` says what it did (restored or deleted the backup), from the `migration-recovered` notice that the gate returns next to `migrated` (§3 "Core modules and API", the write result).
  - Refused, exit 1: files with errors that block the migration (`migration-blocked`, with their issues in the format-spec §16.3 form and order), `newer-format` files, or `write-conflict` (a live backup, or a file changed during the run), with the hint "A migration or another tastelib write may be running; try again, or run `tastelib doctor`."
  - Failed, exit 2: `io-error`. The message says that the library is as it was before the migration, or migrated when the `migrated` notice is there (§4 "Migration runner failures").
- **With `--dry-run`** it only reads: no gate, no recovery, no `.tastelib/`. It plans the migration in memory and prints "Dry run: migrating from format version <n> to <m> would change <x> files, add <y> and remove <z>. Nothing was written.", then the files as above with `would change`, `would add`, `would remove`. A current library gives the "Nothing to migrate" message, exit 0. Files with errors give `migration-blocked` with their issues, exit 1. When a migration backup exists, the files on disk may be half-migrated, so no plan is given: it reports the backup with the code of the `migration-backup` check of `doctor` and "A real run resolves this backup first; see `tastelib doctor`.", exit 1. A dry run leaves the library byte-for-byte unchanged, its listing included.

#### `tastelib doctor --resolve-migration`

`tastelib doctor --resolve-migration [<library>] [--json]` resolves a backup that stays stuck (§4 "Format versions").

1. **Inspect** (read-only). No backup: "There is no migration backup in this library. Nothing to resolve." Exit 0.
2. **Show** the backup: its state; the owner (process id, host name, claim time in UTC and in local time, and whether that process looks alive on this computer); the files a restore would put back and the files it would remove (the manifest's added files); any leftover `owner.json.taken-*` file; and the actions on offer, each with what it does:
   - **restore**, offered only when the manifest is `in-progress` or unreadable (the manifest is written only after every copy is in place, so the copies are complete): puts the backed-up files back, removes the added files (with an unreadable manifest the added files are not known; they stay, and the list says so), then deletes the backup. The library is back at its version before the migration; the next write, or `tastelib migrate`, migrates it again.
   - **delete**, always offered: deletes the backup in the order of format-spec §15.3 step 7 and changes no library file. It is the right choice for `done` (the migration finished) and for no manifest (the originals were never touched). For `in-progress` it warns: "The migration had started writing: some files may be at the new version and others not. Choose delete only if you have already put the library back yourself, for example from Git."
   - **cancel**.
3. **Warn.** Before the prompt, whenever restore is offered: "Restoring overwrites these files with their copies from before the migration: <files>. A change made to any of them since the interruption, for example by a `git pull`, is lost from the folder; it remains in Git history if it was committed." When the owner looks alive on this computer: "Process <pid> on this computer is still running. If it is a tastelib migration, cancel and let it finish. After a crash its id may have been reused by an unrelated program; act only if no tastelib command is running." For an owner on another host: "The owner is on another computer (<host>), or this computer was renamed. Act only if no tastelib command is running there on this library."
4. **Confirm.** Only when standard input and standard output are both terminals and `--json` is not given, it asks "Type restore, delete or cancel:" (only the words on offer). Any other answer, an empty line, the end of input or Ctrl+C cancels: "Cancelled. Nothing was changed." (exit 0). Single letters are not accepted, so a stray key never restores. Without a terminal, or with `--json`, it shows the same details (text, or `result.backup` in JSON) and exits 2 with `not-interactive` — "Resolving a migration backup needs your confirmation: run `tastelib doctor --resolve-migration` in a terminal. Nothing was changed." There is no flag that acts without the prompt: the choice can overwrite the user's files, so an agent or a script may inspect a backup but never resolve one.
5. **Act.** After the answer it inspects again; if anything differs from what was shown (the bytes of `owner.json` or of the manifest, the files listed), it stops with `write-conflict` (exit 1): "The backup changed while you were deciding. Nothing was done; run the command again." Then it claims the backup as a recoverer does (format-spec §15.3 "Taking over a backup"; when there is no `owner.json`, it creates its own exclusively), so no write and no second resolver acts at the same time; a lost claim is `write-conflict`. A restore is durable as recovery case 7. Then the backup is deleted in step-7 order, every `owner.json.taken-*` file included. "Restored <x> files and removed <y>; the backup was deleted. The library is at format version <n>; the next write, or `tastelib migrate`, migrates it again." or "Deleted the backup; no library file was changed." Exit 0. An I/O failure is `io-error` (exit 2): the backup stays, the output lists what was done, and running the command again finishes it (restoring a file from its copy twice gives the same bytes).

#### Output

- **Streams.** In text mode the result goes to standard output and errors go to standard error. With `--json`, standard output receives exactly one JSON document followed by LF, whatever the exit code, and standard error stays empty: errors and notices are inside the document.
- **Language** (maintainer decision). In M1 every message is in English, and the interface language of the config is not used. A pt-BR command line comes later, through a message catalog like the interface's (§12); the text output may then follow the interface language, while codes, `--json` messages and option names stay English.
- **Codes.** Every error and every notice has a stable code from the list below: kebab-case, English, and part of the contract like format-spec §16.2. Messages are not part of the contract and may change. The text output always shows the code: `error <code>: <message>` and `note <code>: <message>`, followed by `hint: …` when there is one.
- **`--help` is the one exception to `--json`.** Help is for people, so `--help` always prints text and exits 0, even when `--json` is on the line; there is no JSON help. Agents learn the commands from this document and the agent kit (§11), not from help text.
- **`--json` of `validate`.** Exit 0 and 1 print exactly the format-spec §16.3 report, which stays the contract. Exit 2 (it could not run) prints the envelope below with `command: "validate"`, so an agent tells them apart by the exit code, or by `reportVersion` against `outputVersion`.
- **`--json` of every other command** is a versioned envelope:

  ```json
  {
    "outputVersion": 1,
    "command": "init",
    "ok": false,
    "result": null,
    "notices": [],
    "error": {
      "code": "already-a-library",
      "message": "The folder is already a library (it has library.json). Nothing was changed.",
      "path": "/path/the/user/gave"
    }
  }
  ```

  - `command`: `init`, `validate`, `doctor`, `resolve-migration`, `migrate`, `config-show`, `config-set`, `config-unset`, `version`, or `null` for a missing or unknown command.
  - `ok` is `true` exactly when the exit code is 0.
  - `result` is the command's own object below, or `null` when the command did nothing. A command that did part of its work before an error (for example `init` with `git-failed`) has both `result` (what it did) and `error`.
  - `notices`: `{ code, message }` objects, in the order they happened, plus `path` when the notice is about a folder.
  - `error`: `null`, or `{ code, message }` plus the details of its code: `argument` for usage errors; `path` for a refused folder; `file` and `field` (`null` when there is none) for `config-error`; `issues` (format-spec §16.3 objects, sorted the same way) for refusals that carry them; `operation`, `file` (library-relative) and `errno` for `io-error`.
  - `outputVersion` changes only when a field is removed or changes meaning. Adding a field, a notice, a code or a command does not change it, so agents must ignore fields they do not know.
- **`result` per command** (absolute paths only as allowed below):
  - `version`: `{ version, supportedFormatVersion, node }`.
  - `init`: `{ libraryPath, libraryId, name, language, createdFolder, gitignore: "created" | "appended" | "unchanged", git: "initialized" | "already-initialized" | "not-requested", configLibraryPath: "set" | "kept" }`.
  - `config-show`: `{ configFile, exists, config }`, `config` being the file's fields as stored (`{ "version": 1 }` when it does not exist).
  - `config-set`: `{ configFile, key, value, media: null | { libraryId, marker: "written" | "kept" | "migrated" } }`.
  - `config-unset`: `{ configFile, key, wasSet }`.
  - `doctor`: `{ library: { path, source: "argument" | "current-folder" | "config" } | null, checks: [{ id, status, code, message, hint, details }], counts: { pass, info, warn, fail, skip } }`, the checks in table order, `code` and `hint` `null` when they do not apply, `details` `null` or the check's own object (the backup inspection, the leftover files, the versions found).
  - `resolve-migration`: `{ backup: null | { state, owner: null | { pid, host, claimedAt, alive }, ownerFile: "present" | "missing" | "unreadable", toVersion, restore, remove, taken, actions }, action: "none" | "restored" | "deleted" | "cancelled" }`, with `alive` `null` for another host and `toVersion` `null` when the manifest is missing or unreadable.
  - `migrate`: `{ dryRun, status: "current" | "migrated" | "planned", libraryFormatVersion, versionsFound, toVersion, changed, added, removed }`, the file lists library-relative and sorted.
- **Exit codes**, extending format-spec §16.1 to every command: **0** the command did what was asked, or there was nothing to do (a cancelled prompt included); **1** the command ran and found problems in the library or the setup, given as issues or failed checks (`validate` errors, or warnings with `--strict`; a failed `doctor` check; a `migrate` or `--resolve-migration` refused with `migration-blocked`, `newer-format`, `write-conflict` or a backup that blocks the dry run); **2** it could not do what was asked: bad arguments, no library, a config error, a refused folder (`init` and attaching), Git missing or failing, an I/O error, no terminal for a confirmation, an older Node, or an unexpected error. An unexpected exception is a bug: it is reported as `internal-error` (exit 2). In `--json`, its message holds only the error's name and, when it has one, its `errno` code (for example "TypeError" or "Error (EACCES)"), never the exception's own message or stack, which can contain absolute paths that no rule above allows. In text mode the full message and the stack go to standard error, for the person who can report the bug.
- **Control characters never reach a terminal raw.** In text mode, every piece of text that can come from a library, a media folder or a path (file names, pointers, messages, hints) is printed with its control and invisible characters (`\p{Cc}`, `\p{Cf}`, `\p{Zl}`, `\p{Zp}`) escaped as `\u` plus four hexadecimal digits, or `\u{…}` above U+FFFF, so a cloned library cannot clear the screen, set the terminal's title or reverse the text (§14 "Threat model"). `core` already escapes the key names it puts into messages; pointers and file names keep the raw text, because a pointer must match the file, so the text printer escapes everything once, in one helper. `--json` is for programs and keeps the values as they are (`JSON.stringify` escapes only U+0000–U+001F); a program that prints them to a terminal escapes them itself.
- **Colors** only in text mode, and only on a stream that is a terminal (`isTTY`), when `NO_COLOR` is unset or empty (no-color.org) and `TERM` is not `dumb`. The command decides this itself and then calls `util.styleText` with `validateStream: false`, because Node's own check lets `FORCE_COLOR` override `NO_COLOR` (checked on Node 26.13.0); `FORCE_COLOR` is not supported in M1. Colors only highlight a severity or a status word; the text says everything without them.
- **Absolute paths.** A message or a `--json` field may show an absolute path only when it is a path this computer's user chose: one given on the command line (or the current folder the command ran in), a path stored in the config, the config file itself, or a folder found above one of those (a Git working tree, a library, a media folder). Files inside a library or a media folder are always shown relative, with `/` (or `media:…`), as in format-spec §16.3. The `validate` report never holds an absolute path (§14), not even the library's.

| `library-inside-media` | 2 | attaching; `doctor` check | the library folder is inside the media folder |
| `media-inside-git` | 2 | attaching; `doctor` check | the media folder is inside a Git working tree |
| `media-marker-unreadable` | 2 | attaching; `doctor` check | the marker cannot be read or is invalid |

The exit column is the exit code of the commands listed; in `doctor` the exit code follows the check's status instead, and `—` means the code appears only there. A format-spec §16.2 code takes its exit code from where it appears: 1 in `validate` and `migrate` (an issue found in the library), 2 when attaching refuses the folder given (`media-folder-mismatch`, `newer-format`).

## 5. Capture

Capture happens on the computer, in the app, by pasting, dropping or choosing a file:

- **Screenshots and images**, stored compressed (WebP).
- **Page URLs**, captured as a full-page image by a headless browser, on the user's request only.
- **Videos and GIFs**, for motion; stored compressed, with frames extracted for pinning.

The reference records how it was captured in `source.via`: `paste`, `drop`, `file-picker` (a file chosen with the app's file chooser) or `url-capture` (format-spec §7.1; see "File picker" below).

New captures land in an **inbox** until processed.

**(to specify in M2)** size limits, compression settings, capture timeouts, frame extraction.

### No metadata in the media folder

Every media file that the tool writes to the media folder keeps no metadata from what the user pasted, dropped or chose: no EXIF (which can hold the GPS location, the camera or phone, the owner's name and the date), no XMP, no IPTC, no comments or text chunks, no embedded thumbnail, and for videos no container metadata (creation time, location, device). Only the pixels (and, for video, the frames and timing) reach the media folder. Re-encoding drops most of it on its own; whatever path #44 chooses, including a file kept without re-encoding (for example one already small enough), must remove it too, so a pasted file is never copied into the media folder with its metadata. An embedded ICC color profile from the user's file is never copied either, because a custom profile can carry text (its description, copyright and device fields): either the pixels are converted to sRGB and no profile is written, or the file carries only a known standard profile (the exact bytes of a standard sRGB or Display P3 profile) that the tool writes itself. #44 chooses between the two. #44 also decides how metadata is removed and adds a test that proves it on generated files carrying each kind of metadata: EXIF with a GPS location, XMP, IPTC, comments and text chunks, an embedded thumbnail, video container metadata, and a custom ICC profile with personal text in it. URL captures come from the browser's own screenshot, so they carry nothing from the user's files; the same rule still applies to what the encoder writes.

The reason: media is synced and may be shared in packs (§10), while the user pasted it only for how it looks. A screenshot from a phone, or a photo of a screen, can say where the user lives; that must never leave the computer by accident (§14).

### Tall and wide captures

WebP stores at most 16383 pixels on each side. An image or page capture taller than that (a long full page, a tall screenshot) is split into several **segments**, each its own media item of the same reference, in order from the top (`m1` is the top segment, then `m2`, …); a capture wider than the limit is split the same way from the left. It stays format v1: a reference holds 1–50 media items (format-spec §7.1), and a segment is an ordinary media item of kind `image` or `page`. If #44 chooses a format with another limit, the split follows that format's limit. #44 sets the segment size, whether segments overlap, what happens past 50 segments (for example, downscale or refuse) and what happens to an image over the limit on both sides.

- **`p0` on a split capture.** format-spec §7.4 as written in M0 said that `p0` covers "the whole first media item", which for a split capture is only its top segment.
  - *Maintainer decision (2026-11-05):* the format stays v1, and consumers (the app, exports, agents reading files) treat `p0` as covering **every segment of a split capture**: the app shows the whole-reference note against all of them, and an export's whole-image view of `p0` (§10) shows every segment, in order.
  - *Derived rule (maintainer confirmed, 2026-11-05):* format v1 has no field that marks which media items are segments of one capture, so the only rule consumers can apply to v1 data without guessing is that **`p0` covers every media item of the reference, in id order**. For a reference with one media item this is exactly format-spec §7.4; for a split capture it is every segment; it also covers media the user adds later (below), which the decision itself does not settle. If the maintainer wants segments only, consumers need a field that marks them, which is a format change the decision rejected.
  - format-spec §4.3 and §7.4 say the same; no schema, field or validation rule changed.
- **Pins** stay on one media item each (`mediaId`, format-spec §7.3), so a pin lies within one segment. How the app shows segments together and what it does with a box drawn across a seam is decided with pins in M2.

### Adding media to a reference

The user can add media items to an existing reference (another screenshot of the same screen, a video of its motion), by pasting, dropping or choosing a file in the reference view. Each new item takes the next number: `lastIssued.media` plus one, then `lastIssued.media` is raised (format-spec §4.3); a number is never reused, even after its item is removed. An added tall image is split into segments like a new capture (above), and the 50-item limit counts every item of the reference. The same metadata rule applies. `source` keeps recording how the reference was first captured and is not changed by adding media. A URL capture always creates a new reference, because `source.url` names one page. Agents cannot add media: format-spec §13.1 reserves media to the user, and `tastelib` refuses it with `not-allowed`.

Because `p0` covers every media item (the derived rule above, confirmed by the maintainer), adding media changes what `p0` covers. When the reference's `p0` interpretation is `to-review` or `accepted` (the states `proposal-stale` covers, format-spec §13.4), the app offers, right after the media is added, to reopen it, as it does for a stale note: the interpretation was made without the new media. No `validate` code reports it and nothing is stored to remember it, because format-spec §13.4 limits staleness to the note in v1.

### File picker

The app's file chooser is the third way to bring in a local file, next to paste and drop, and the reference records it as `source.via: "file-picker"`. Format v1 as written in M0 allows only `paste`, `drop` and `url-capture`. The maintainer decided (2026-11-04) to **amend format v1** to add `file-picker`, instead of making it format v2, because no tool had written a v1 file yet (§18). This reverses the "v1 is frozen" decision of §18 for this one value only; every other change still needs a new format version. format-spec §7.1 holds the value and §15.1 records the amendment, and the golden v1 library holds a reference with it.

### URL capture

- **Browsers** (maintainer decision, 2026-11-04): Chromium and Firefox are both supported. #45 chooses the engine (one that drives both, or one per browser), how each browser is obtained and found on Linux, Windows and macOS, and the oldest versions supported. A browser is downloaded only by an explicit command the user runs, never on its own (rule 5); that this command counts as part of the URL capture the user asks for, and so is allowed by rule 5, awaits the maintainer's confirmation (§18).
- **Firefox and rule 7** (maintainer decision, 2026-11-04): Firefox is MPL-2.0. A browser that the tool starts as a separate program, installed by the user or by that explicit command, and that is not bundled, copied or modified by the tool, is accepted under rule 7. The tool links no browser code; it only talks to the browser over its control protocol. The same reading covers Chromium. The engine library that drives the browsers is an ordinary dependency and must meet rule 7 itself (#45).
- **Network rules** (maintainer decision, 2026-11-04): every request a capture makes, not only the URL the user gave, is refused when it goes to a loopback, private, link-local, shared (CGNAT), multicast or unspecified address, in IPv4 or IPv6. That includes redirects, subresources, WebSocket and WebRTC, and the address actually connected to is checked, so DNS rebinding does not get around it. #45 decides how, the same way in both browsers. Tests capture pages from a loopback test server through an address policy that only test code can inject, never reachable from the config, the API or the command line (#45).
- **Consequence:** a page served from the user's own computer or local network (a development server on `localhost`, a router's page) cannot be captured by URL. It is captured as a screenshot and pasted instead. The reasons are in §14.

## 6. Notes and pins

- Each reference has a **free-text note** in the user's own words.
- **Pins** are boxes drawn on an area of an image or of a video frame. Each pin is a **piece** with its own note. The whole-reference note counts as a piece covering the whole reference: every segment of a split capture, and every media item under the derived rule of §5 "Tall and wide captures".
- A pin is **positive** (take this) or **negative** (not this). Negative pins are the source of **guardrails**. There are no whole-image anti-references.
- Regions are stored as proportions (0–1) of the media size, so they survive resizing.
- The whole-reference note is piece `p0`; pins are `p1`, `p2`… A pin on a video sits on one of its extracted frames. Pieces are addressed across the library as `<ref-id>#p<n>`.
- A reference can hold several media items: the segments of a tall capture, and items the user added later (§5). `p0` covers every segment of a split capture (maintainer decision) and, under the derived rule confirmed by the maintainer, every media item of the reference, in id order (§5 "Tall and wide captures"); each pin sits on one media item, which it names.
- The app stores notes exactly as typed; the only change is that line breaks are stored as `\n`. A note that breaks a rule (for example, a control character) is refused with a message, never silently altered.

## 7. Interpretation and review

- Interpretation runs in **batches through an agent** ("process my new references"). For each piece, the agent proposes vocabulary, keywords, screen types, components, design aspects and, for negative pins, a guardrail.
- Everything the agent writes is marked **`to-review`**. In the app, a review queue offers **Accept**, **Correct** or **Reject**. A correction is the user's complete version, stored next to the original proposal, which is never modified after review. Rejected proposals are kept, so agents see what the user refused and do not propose it again.
- The user's own words are never altered.
- Agent writes are an allowlist (format-spec §13.1): through `tastelib` (CLI or MCP), an agent can only add proposals marked `to-review` (piece interpretations, new families, glossary terms, guardrails, profile statements, directions, an intent with its discarded list, and pieces proposed for a family), set the links of an entry it created while that entry is still `to-review`, and replace an agent proposal while it is still `to-review`, whoever proposed it (`proposedBy` is updated). Everything else is refused with `not-allowed`: references (capture, media, pins, notes), names, user-authored values, corrections, review statuses, links of reviewed entries, reopening, deleting and merging. Those are the user's, in the app.
- While a proposal is `to-review`, an agent may replace it. Once reviewed, an agent cannot replace or delete it; the user can reopen it, and only then can an agent propose again.
- `tastelib` records a fingerprint of the note each proposal was based on. If the user edits the note later, the proposal is flagged as stale and the app offers to reopen it.
- Until it is reviewed, a proposal is **tentative**: shown as such and not exported as the user's taste unless the user chooses to.
- Who writes which field, and the effective value consumers use, are specified in [format-spec.md](format-spec.md) §13.

## 8. Organization and taste tools

- **Aesthetic families emerge** from the collection. The agent proposes a name, a meaning and a vocabulary; the user accepts, renames or merges.
- Browsing also works by **screen or page type**, **component** and **design aspect**.
- Taste tools: **family pages**, a **taste profile** (likes, rejections, contradictions), a **vocabulary glossary**, and **side-by-side comparison**.
- A family's pieces are listed in the family; the agent proposes pieces, and the user accepts or rejects each one. A family's slug is fixed at creation; renaming changes its name only. Merging moves the pieces and replaces links to the merged family.
- The taste profile is stored as separate statements, each reviewed like any proposal. Its Markdown view is rendered when needed, not stored.
- Guardrails are proposed from negative pins into one list of candidates; a candidate becomes approved when the user accepts or corrects it.

**(to specify in M4)**

## 9. Project spaces

- A project space pulls pieces from the library and adds its own layer: intent, directions, packs and results.
- **Intent:** the agent drafts it from any briefing dropped in, keeping only what, for whom, what users must do and why. Visual decisions, styles, colors, fonts and named directions are filtered out and listed as **discarded**. The user edits the result.
- **Directions:** the agent proposes about five (family + pieces + why it fits); the user adjusts.
- **Results loop:** screenshots of generated versions are pasted back into the project and pinned. They become references that sharpen the next packs and the taste profile. A result is an ordinary reference that names its project and direction; there is no separate results store.
- The briefing itself is not stored in the library: only the intent drawn from it and the list of what was discarded. Agents never use the discarded list as input for directions, packs or prompts.

**(to specify in M5)**

## 10. Export

An export is a folder `pack-<date>/` with:

- `README.md`: how to use the pack (directions side by side, then the build sequence).
- One subfolder per direction with `prompt.md` (Aesthetic · References · Intent · Guardrails), `image-prompts.md`, and `refs/` (a crop of each piece plus the whole image with the area highlighted).

## 12. Internationalization

The interface is in English with a Brazilian Portuguese option from the first release. All user-facing strings go through the translation layer from day one. The README has a pt-BR translation in `docs/pt-BR/`.

**Translation layer.** A small in-house layer in `web`, no dependency (§18); its files are described in its code. Components never contain literal user-facing text. The first language is taken from the browser preferences (the first `en` or `pt` tag decides, and `pt-*` gives `pt-BR`; otherwise `en`) and a selector switches it at once. The interface language is a per-machine setting (§4). ## 13. Portability

- Linux, Windows and macOS (Apple Silicon) are all first-class and verified in CI.
- No script that runs on only one operating system. Git hooks are POSIX `sh`, which Git runs on every platform. Workflow helper scripts are plain Node (`.mjs`, no build step, no dependencies), which runs on every platform.
- Text files use LF (`.gitattributes`); the tool reads either line ending.
- Library files are UTF-8 without a BOM, LF, in a canonical JSON form (format-spec §3), so the same data gives the same bytes on every system.
- File names inside a library and a media folder come only from identifiers (ASCII, lowercase, never a Windows reserved name), so they behave the same on case-insensitive file systems and never depend on Unicode normalization. Only the folders the user chooses may have non-ASCII names.
- Paths with non-ASCII characters (for example `Usuário`) are tested in CI. macOS file systems may return such a name in a different Unicode normalization (NFD) than the one passed in, so a path the user gave is stored verbatim, and when a name from a directory listing is matched against a given one, both are compared after `normalize("NFC")`; equality of the raw strings is never assumed.

## 14. Security

See [SECURITY.md](../SECURITY.md) for the sensitive surfaces. The local server listens on the loopback interface only and rejects cross-origin requests.

**Threat model.** The tool is used by one person, on their own computer, with their own account. This list says which conditions the tool must handle and which it need not. A review grades its findings by it and by promises (the `continue` skill, step 6; the full list is in `.claude/agents/reviewer.md`): code that breaks a promise or a contract of this document or of format-spec, or a hard rule, under a condition in scope, is a blocker, and so is a change to what users or agents see that the docs do not record; the same problem under a condition out of scope is minor. Code that differs from a description of mechanism is not a blocker: the fix is to remove the description.

- **In scope:**
  - **The user's own mistakes:** a hand-edited file with typos, wrong types, duplicate ids or broken links; a hand-resolved Git merge; a file deleted or moved by hand.
  - **Other computers:** files that arrive through `git pull` or a sync service, including older or newer format versions, and media that has not arrived yet.
  - **Interruptions:** a process that is killed, and a power cut during a write, within the durability rules of §4 ("Writing library files", "Durability").
  - **Two `tastelib` writers at once** (the app and an agent), within the optimistic check of format-spec §5.
  - **The three platforms as people really set them up:** Windows files held open by an antivirus, a sync client or an editor; macOS Unicode normalization and case-insensitive file systems; non-ASCII paths; symbolic links and junctions the user made to move a folder (for example the media folder, or the whole library folder, on an external drive; a folder or file inside the library that leads outside it is not a supported setup, §4 "Reading library files", "Links stay inside the library"); a drive that is not mounted; a folder the user cannot read.
  - **Untrusted content the tool consumes:** captured pages and URLs, briefings, media files, and a library cloned from someone else, including the symbolic links it carries. Such input must not run code, make a write follow a link at a file path (the rename replaces the link itself), make a read or a write leave the library folder through a link or a junction (a file or a format folder that leads outside, or into `.tastelib/` or `.git/`, is `unreadable-file` and is neither read nor written, and a `.tastelib/` that leads outside refuses every write; §4 "Reading library files", "Links stay inside the library"), make a media path resolve outside the media folder (format-spec §6.2), exhaust memory past the limits of §4 ("Reading library files"), hang the tool (a link to a special file such as `/dev/zero` is `unreadable-file`, as the reader already does), or put terminal control characters into its output. Other links that stay inside the library are followed. A library cloned on Windows without symbolic links enabled in Git gets each link as a small text file holding its target, which the tool treats as any other file of that name (for example `invalid-json` where a library file belongs), so nothing outside is touched there either.
  - **Agents,** which write only through `tastelib`, within the allowlist of format-spec §13.1.
- **Out of scope:**
  - **Someone who already controls the user's account** (or the administrator). They can change any file directly, so no check in the tool stops them.
  - **Special files** (FIFOs, sockets, devices) that the user's own account created at a library or media path. Git and sync services carry only regular files and symbolic links, so nothing else can put one there. A symbolic link that arrives through Git or a sync service and leads to a special file is in scope (untrusted content, above).
  - **Races with programs other than `tastelib`** that change the file system between two system calls, beyond the windows that format-spec §5 already accepts.
  - **Storage that breaks its own guarantees:** a drive or file system that ignores `fsync`, reorders writes past it, or corrupts data at rest.
  - **Unusual permissions set on purpose** (a folder that can be listed but not entered): the tool reports an error, but how many issues it reports is not a requirement.
  - **Redundant issues and wording:** a second issue caused by a value that already has its own, or a message that could be clearer while it still names the field and what is expected (format-spec §16.3). The user still sees the real problem. A problem that is not reported at all, or a wrong code or severity, is in scope.
  - **Mechanisms of later milestones.** Their failure modes are designed by the issue that builds them, not by an issue that only mentions them.

Library and media paths are built only from identifiers that match the format's patterns, and a media path that resolves outside the media folder (for example through a symbolic link) is refused (format-spec §6.2); a library file or folder that leads outside the library, or into its `.tastelib/` or `.git/`, through a link is neither read nor written (§4 "Reading library files", "Links stay inside the library"). JSON files over 8 MiB are not parsed, and nesting deeper than 64 levels is refused before any schema or recursive code sees it (§4 "Reading library files"). Validation reports name files relative to the library and never print absolute paths. The command line starts external programs (only `git`, for `tastelib init --git`) by an absolute path found in the absolute entries of `PATH`, never by name and never from the current folder or a folder it works on, so a program planted in a library folder never runs (§4 "Command line").

**Personal data in media.** Media files keep no metadata from the user's files (EXIF with its GPS location, XMP, IPTC, comments, video container metadata, an embedded ICC profile), so a pasted screenshot or photo never carries where or on what device it was taken into the media folder, a sync service or an exported pack (§5 "No metadata in the media folder"; #44 decides how).

**URL capture reaches only the public internet.** A captured page is untrusted content running in a real browser on the user's computer. Every request it makes to a loopback, private, link-local, shared, multicast or unspecified address is refused, including redirects, subresources, WebSocket and WebRTC, and the address actually connected to is checked (§5 "URL capture"; #45 decides how). Otherwise a page could reach the tool's own local server (which listens on loopback), a development server, a router's admin page or other devices on the local network, and its screenshot could bring what they show back into the library. The browser is a separate program the user installed or asked to download, started with a fresh temporary profile (#45), so a capture never sees the user's own browsing data.

**(to specify in M2)**

## 15. Testing

- Unit tests next to the behavior; pure logic (schemas, parsers, naming, the intent filter, migrations) always has them.
- End-to-end tests drive the app in a browser.
- Test data is **synthetic and generated at test time**. No third-party images, pages or videos are ever committed.
- CI runs every check on Linux, Windows and macOS, including a non-ASCII path and both line endings in inputs.
- Required checks: CI runs `tastelib validate --strict --checksums` on the golden v1 library (§15 "Format and migration tests"), with its media folder generated at test time, and fails on any error or warning; migrations are tested; a made-up briefing full of visual decisions must leak none of them into the intent, and the discarded list must show them all. The sample library with freely licensed media (`examples/sample-library/`) arrives in M7 (§16) and is then validated the same way in CI.

Where the decisions behind these tests live: the core modules and API in §3 "Core modules and API"; the reader, the write pipeline, the gate, migration failures and the index in §4 (the table "Where each rule lives"); the command line and how its tests run in §4 "Command line".

### Test layout

- **Unit tests** use Vitest (5.1.0). They sit next to the code as `src/<name>.test.ts`, are excluded from each package's build (`tsconfig.json` excludes them) and are type-checked by a `tsconfig.test.json` in the package (see `packages/testkit`). Every package except `e2e` has a `test` script (`vitest run`, with `--passWithNoTests` while a package has no tests yet; `core`'s is `tsc -b && vitest run`, see "Concurrency" below); the root `pnpm test` runs them all and is part of `pnpm check` (§3). A package that gets its first test also gets `tsconfig.test.json`, its reference in the root `tsconfig.json`, and a `devDependencies` entry for `@tastelib/testkit` when its tests use it.
- **End-to-end tests** use Playwright (`@playwright/test` 1.64.1) in `packages/e2e`, as `tests/*.e2e.ts`. They are not part of `pnpm check`, because they need a browser download (about 120 MiB). First time: `pnpm test:e2e:install`; then `pnpm test:e2e`, which builds `testkit` first because the tests import its `dist/`. Each test starts its own local HTTP server on an OS-assigned port and serves generated content; nothing touches the network. The package has no `test` script on purpose, so `pnpm test` skips it.
- **Shared helpers** live in `packages/testkit` (`@tastelib/testkit`, private, dev-only). It has no workspace dependencies and nothing ever lists it under `dependencies`. `core` stays free of other workspace packages at runtime; once `core` has tests it lists `testkit` as a `devDependency` only (a test-time edge, not part of the dependency graph in §3). It offers:
  - PNG and BMP images built byte by byte (no image library), deterministic per seed: the same pixels always, but PNG bytes are stable only within one Node version, because zlib output can change, so tests that need exact bytes use BMP or the byte-stable PNG. JPEG and WebP fixtures arrive with the encoder chosen for compression (M2).
  - The byte-stable PNG and the seed hash of the golden media (below, "Format and migration tests").
  - Small HTML pages, with either line ending.
  - A seeded PRNG behind the images, identical on every platform.
  - A fresh temporary directory whose path contains non-ASCII characters, removed afterwards.

  Their signatures and options are documented in `packages/testkit/src`.
- **Determinism:** fixed seeds, no real network, no dependence on directory listing order or locale; tests that list directories sort the result.
- **No committed binaries:** images are generated at runtime; CI's media check enforces it.

### Format and migration tests

- **Golden libraries.** `packages/core` keeps one hand-written, synthetic fixture library per released format version (JSON only; media is generated at test time), at `packages/core/test/golden/v<N>/`, which is itself a library folder (`library.json`, `references/`, …). A fixture is frozen once its version is released: it is never edited, only added to.
- **Golden media are byte-stable.** The frozen JSON records each media file's `bytes` and `sha256`, so the media a test generates for it must never change. `testkit` has a byte-stable PNG: written byte by byte with uncompressed ("stored") deflate blocks and hand-written CRC-32 and Adler-32, so its output depends on no zlib and no Node version, with a test that pins the SHA-256 of a few outputs. The golden media folder is written from the golden JSON: the marker with the library's id, and for each media item and frame an image from `makeStablePng` with the listed width and height and, as seed, the 32-bit FNV-1a hash of its media path. The golden libraries therefore list only `image/png` media, with small sizes (at most 64 × 64), and no video until a byte-stable video generator exists; a video reference is then added as a new file (fixtures are only added to). Validating a golden library with its generated media folder and `--checksums` gives no warning, and without a media folder only `media-not-checked`.
- **Schemas** have positive and negative tests for every rule in format-spec, including the canonical serializer (same data, same bytes; `not-canonical` on BOM, CRLF and wrong order) and non-ASCII text in notes.
- **Each migration step N → N+1** is tested for: the golden vN library migrates to a library that validates against the vN+1 schemas; the specific changes the step makes; determinism (two runs give identical bytes); files already at vN+1 pass through unchanged; an interrupted run (stopped after some writes, with the manifest still `in-progress`) is restored from the backup and reaches the same result as an uninterrupted one; the same for an interrupted migration of a library with mixed file versions, where `library.json` is already current; a crash while copying the backup (owner gone, no manifest yet) leaves the originals untouched, and the backup is deleted without restoring; two concurrent recoverers of an `in-progress` backup with a dead owner: only one wins the `owner.json` rename and restores, and the other re-checks and does not restore; a slow recoverer that renames the new `owner.json` of one that already took over finds different bytes, puts the claim back, and does not act; a migration still copying (owner alive, no manifest yet) is not deleted by a second writer, which gets `write-conflict`; a backup folder with no `owner.json` yet, or with an owner on another host, is treated as live; an unreadable manifest is not deleted (the write gets `write-conflict` and the backup is kept); `owner.json` is removed last when a backup is deleted; a backup marked `done` whose owner is gone is deleted without touching the files; and with two concurrent migrations only one claims the backup folder, while the other gets `write-conflict` and does not restore the backup of a live owner.
- **The chain:** the golden v1 library migrates through every step to the current version and validates. A test fails if `CURRENT_FORMAT_VERSION` has no step module, schema folder and golden library for every version up to it.
- **Validate** has one test per issue code (format-spec §16.2), checking severity, file, pointer and exit code, on Linux, Windows and macOS and under a non-ASCII path.
- **Writes** have tests for every allowed agent write and for refusals with `not-allowed` (one per refused kind in format-spec §13.1), for `write-conflict` (the file changes between read and rename), for a multi-file write that stops partway (the primary change is kept, only `dangling-link` warnings remain, and the report lists the files written and not written), for slug derivation (a long name, a name that shortens to a reserved word, a taken slug near 64 characters), for clock skew (a lower bound in the future), and for sequential ids that are never reused after a deletion.

### Core test approach

- **Where test-only code lives.** Unit tests stay next to the code (`src/<name>.test.ts`). Everything else that only tests use sits in `packages/core/test/`, outside `src/`, so the build can never put it in `dist/`: `tsc` refuses an import of it from any build file, because it lies outside `rootDir` (`src/`), and the lint rule of §3 also reports it in pure modules:
  - `test/golden/v<N>/`: the golden libraries (above);
  - `test/support/`: builders of synthetic libraries (among them the large library of the performance budget, deterministic per seed, with every file settled), fault-injecting file systems and pause points, each documented in its own file;
  - `test/migrations/` and `test/schemas/v2/`: the test-only step and schemas (below);
  - `test/processes/`: plain `.mjs` drivers that child-process tests start.

  `packages/core/tsconfig.test.json` type-checks all of it but the `.mjs` drivers, which are plain JavaScript that Biome lints. Helpers that do not depend on `core` (byte-stable images, temporary folders) stay in `testkit`; the builders depend on `core`'s types, and `testkit` can never depend on `core` (§3), so they stay in `core`. Tests of other packages that need the golden library find it by path from the repository root; it is data, not a package import.
- **Biome never formats the golden libraries.** Its JSON formatter rewrites canonical JSON (for example it puts `["calm", "dense"]` on one line), so `biome.json` excludes `packages/core/test/golden/**`; otherwise `pnpm format` would edit frozen fixtures. `.gitattributes` already keeps them LF on every checkout.
- **The migration runner at version 1.** The runner and the reader take the format registry (`format.ts`) as a parameter; production passes the real one (`CURRENT_FORMAT_VERSION` 1, no steps). Tests pass a test registry with version 2: test-only v2 schemas in `test/schemas/v2/`, built from the v1 modules with zod's `safeExtend` and the changes below, a v2 folder layout, and a test-only step in `test/migrations/v1-to-v2.ts` that is pure and deterministic like a real one and does each thing a real step may do: it sets `formatVersion` 2 in every file (changes), splits `glossary.json` into one file per term at `glossary/<term-id>.json` (adds files and removes one, so the manifest's added files and the deletions run), and copies `library.json`'s `language` into each `project.json` (moves data between files). Every runner test of §15 above runs with it: the golden v1 library migrates and validates against the test v2 schemas, determinism, pass-through of files already at v2, mixed versions, interruption and recovery.
- **Runner failures.** With injected I/O errors after the claim, after the manifest, after some step-5 writes and after `done`, a migration cleans up its own backup: the library is byte-for-byte as before (or migrated, after `done`), no backup is left, the result is `failed`, its `notices` hold `migrated` only in the case after `done`, and the next write in the same process succeeds. After some step-5 writes, only the files already replaced or deleted are restored and only the added files it created are removed; a file it had not reached is never touched. A file changed outside `tastelib` before its step-5 write gives `refused` with `write-conflict`, the files written before it are restored, and the changed file keeps its new bytes. A file changed between step 1 and the re-read after the claim (changed once before the `mkdir` claim, and once from the `claimed` hook) gives, in both cases, `refused` with `write-conflict` before the manifest: the backup is deleted (`owner.json` last), no copy holds the old bytes, and every library file is untouched. When the cleanup fails too (an injected error during a restore), the backup stays, a second runner (another injected `pid`, probe `alive`) gets `write-conflict`, and the next write in the owning process finishes the cleanup first, accepting files already restored or removed by the interrupted cleanup (a cleanup interrupted after removing an added file and before restoring a deleted one is finished by the resumed cleanup: the added file stays absent and the deleted file comes back with its backed-up content), but not if `owner.json` no longer holds its bytes, and not past a file in any other state (`write-conflict`, backup kept). A crash (`SimulatedCrash`) at the same points cleans up nothing.
- **The chain test at version 1** checks that the production registry's versions are exactly 1 to `CURRENT_FORMAT_VERSION`, with a step for each version below the current one and no other; that for every version there are `src/schemas/v<N>/set.ts` and `test/golden/v<N>/library.json`, and for every version above 1 `src/migrations/v<N-1>-to-v<N>.ts`; and that every golden library migrates through the production chain to the current version and validates with no error and no warning (at version 1: no step, and the golden v1 library validates). The same chain logic also runs once with the test registry, so it is exercised with a real step before the first real one exists.
- **The media marker** has its own registry (version 1, no steps), separate from the library's (format-spec §15.1), passed the same way. Its tests inject a test-only marker step v1 → v2 (it sets `formatVersion` 2 and adds one field) with a test-only v2 marker schema, also under `test/`, and check: an older marker is migrated on disk when the folder is attached or written to, and in memory only by read-only commands; a newer marker blocks media writes while the library stays writable; and the marker never counts for `mixed-format-versions`.
- **Crash points.** The file-system modules use a small file-system adapter (the subset of `node:fs/promises` they need) and accept hooks: `fs` (default the real one), `probe` (`(pid) => "alive" | "gone"`), `hostName` and `pid` (default `os.hostname()` and `process.pid`), `platform` (for the Windows retry path) and `at(point)`, called at every named step of the runner and of recovery (`claimed`, `owner-written`, `copied:<path>`, `manifest-written`, `wrote:<path>`, `library-json-written`, `done-written`, `deleted:<path>`, `owner-deleted`, `taken`, `own-owner-written`, …), of the write pipeline and of the replace primitive (their points are documented with their options in the code). The deletion tests crash at every point of a deletion of each kind and check that `validate` then reports no error, only `dangling-link` warnings (and `leftover-temp-file` after a crash inside a replace), and that running the deletion again clears them; a conflict or an I/O error at each file gives only `dangling-link` warnings and the files written and not written. A test simulates a crash by throwing `SimulatedCrash` from `at`: it carries no `errno` code, so no result path catches it and nothing is cleaned up (§4 "Cleanup only on result paths"), as when a process dies. The "dead" owner is then reported `gone` by the test's probe, and a second runner (another injected `pid`) recovers. A wrapping file system injects I/O errors (`EPERM` on a rename a given number of times, `EIO`, `ENOSPC`) the same way.
- **Concurrency.** The orderings of the takeover protocol (two recoverers, a slow recoverer that takes the new claim of a winner, a writer meeting a migration still copying) are tested deterministically in one process: `at` returns a promise, so a test pauses one runner at a named point, runs the other to a point or to the end, then resumes the first. Real child processes (`process.execPath` with a driver in `test/processes/`, which imports the built `dist/`) cover what only the operating system can show: eight processes racing for the non-recursive `mkdir` claim (exactly one wins, the others get `write-conflict`), and a process killed after its claim, whose process id the real probe then reports `gone` on Linux, Windows and macOS. `core`'s `test` script is `tsc -b && vitest run`, so `dist/` is current when the drivers run. The drivers cannot import the test-only registry (TypeScript under `test/`, never built), so the claim race uses a version 2 the driver builds inline from the production version 1, which only sets `formatVersion` 2.
- **The process probe** calls `process.kill(pid, 0)`: `ESRCH` means gone; success or any other error (`EPERM`: alive but not ours) means alive, so in doubt the backup is treated as live, never deleted. Node documents signal 0 as "a platform independent way to test for the existence of a process"; on Windows, libuv opens the process and checks that it has not exited. A `pid` in `owner.json` that is not an integer from 1 to 2^31 − 1 makes the file unreadable (case 1 of format-spec §15.3): `process.kill(0, 0)` and `process.kill(-1, 0)` signal a process group or every process and always succeed (on Windows, pid 0 means the current process), and Node refuses pids above 2^31 − 1.
- **The performance budget** (§4 "Index") is an ordinary test in `pnpm test`: it generates the library in a temporary folder (not timed), opens it once untimed to warm up, then times each budget line three times and checks the fastest run (§4 "Index", "Three runs"); a line that changes the library changes it again in each run, and the library is settled with an untimed refresh before each write, so every run does the same work, and the test checks that each write started from that settled snapshot. It runs alone, after every other test file of `core`, in one worker (configured in `packages/core/vitest.config.ts`), because a timed line that shares the runner's CPUs with other test files measures them too. Each line passes under its absolute budget or within `factor × baseline + overhead` (§4 "Index", "Performance budget"), with the factors and overheads as named constants in the test. The baselines are measured the same way, three times each with the fastest kept, on the same files just before the line: a plain `stat` of every file with 16 in flight and a `statSync` loop before every line, plus a plain read and `JSON.parse` of every file before opening, and one plain write of a reference's bytes with `fsync` and rename (in a folder beside the library) before the write. The helper that picks the fastest run has a unit test that fails if it returns the first or the slowest run. Every run logs, and each failure message says, the three times of the line and which one was checked, both bounds, the baselines, and where the time went in the checked run: the listing, the `stat` calls and the reads.

The check command is in §3.
